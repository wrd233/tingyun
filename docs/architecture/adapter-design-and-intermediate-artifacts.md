# Adapter 设计思路与中间产物说明（整理稿）

> 本文档是当前 adapter 设计思路与中间产物体系的主设计文档。

## 1. 文档定位

这份文档聚焦于 adapter 这一层的整体设计思路，以及 adapter 在整个工作流中需要产出的中间对象、中间文件和证据材料。这里不把 adapter 当成简单的平台代理，而是把它视为一个“诊断中间层”：它既要服务于对象发现和深挖，也要服务于后续写报告和复核。

本文尽量复用我原本的语言，只对结构进行整理，并在我有把握的地方做适当补充，使 adapter 的职责、边界和中间产物的角色更清楚。

## 2. Adapter 在整个项目中的定位

我并不希望 adapter 只是把听云 APM 的接口原样镜像出来。它不应该只是“把请求调出来”，而应该有自己的一套处理思路。

这套思路至少包含以下几层目标：

1. 帮助我识别哪些对象值得纳入考虑。
2. 围绕这些对象做进一步的深挖。
3. 分析对象之间的关系、成因与更全局的背景。
4. 把前面得到的信息转成更适合写报告和复用的输出形式。

因此，adapter 的定位不是“平台代理”，而是“围绕诊断与报告的中间层能力”。

它一方面连接听云 APM 平台，另一方面又要面向 client、Codex、ChatGPT 等下游消费方提供更干净、更有语义、更可控的结构化能力。

## 3. 我希望 adapter 支撑的整体工作流

在我的设想里，机器 A 上运行 adapter，机器 B 上运行 client 和 agent。机器 B 不直接面对听云平台，而是通过远程调用机器 A 上的 adapter 来获取素材。

这种方式的好处是：

- 听云 token、真实调用能力和配置集中在机器 A 管理；
- 机器 B 更稳定地消费结构化 pack，而不是原始平台接口；
- agent 可以把更多精力放在对象筛选、证据整理和分析表达上，而不是重复处理平台细节。

因此，adapter 一定要输出足够适合后续消费的中间层产物，否则后续所有分析都会被迫下沉到平台字段层面，既重、又乱、又不稳定。

## 4. Agent 侧素材构建的三个阶段，以及 adapter 对它们的支撑

我当前对 agent 侧的理解，是它不应该一上来就“写结论”，而应该先分阶段生成高质量素材。adapter 的价值，就在于为这三个阶段持续供给合适的能力和中间对象。

### 4.1 第一阶段：宽入口发现与初步收束

第一阶段的目标，是从全量对象中寻找并罗列出值得进一步观察的重要对象。这里强调“宽入口”，也就是先尽可能覆盖，再通过启发式原则逐步收束，把最终待观察对象的数量控制在一个人真正看得过来的范围内。

这些对象可以是接口、SQL，也可以扩展到其他诊断对象。第一阶段的关键不是立刻给出根因，而是：

- 拿到尽可能全量、可表格化的信息；
- 用脚本而不是纯自然语言来做第一轮预处理和排序；
- 尽量在这一层就形成后续可以复用的表格；
- 让这些表格既能作为下一阶段的输入，也能成为最终报告中的素材来源。

从这个角度看，第一阶段的重点是：先把“值得看谁”这件事情做成结构化、可复用、可调参数的过程。

我当前更偏向于：**每一类对象各有一张主表。**

这意味着：

- 接口有接口自己的主表；
- SQL 有 SQL 自己的主表；
- 之后如果扩展到外部依赖、拓扑节点或其他对象，也可以有各自的主表。

这种划分方式更符合我后续阅读、筛选和写报告的习惯，也更利于在不同对象类型下保留各自更有语义的字段。

### 4.2 第二阶段：围绕对象深挖，并持续更新中间对象

第二阶段是在第一阶段已经初步收束对象之后，对这些对象逐个进行深挖。此时关注的已经不只是“它看起来慢”或“它错误率高”，而是：

- 它的典型 trace 是什么；
- 它处在什么拓扑关系里；
- 它慢在哪里，慢的主体是谁；
- 它与哪些下游依赖、共享路径、公共代码段或其他对象有关；
- 它当前的异常是否只是某个更大问题簇的一部分。

在这一阶段，中间对象不会静止不动。前面筛出来的待观察对象表格，不是一锤子买卖，而是会持续被修改：

- 某些对象会被进一步确认，因此重要程度上升；
- 某些对象在深挖后会被排除或降级；
- 某些对象之间会被发现存在关联，因此需要被合并看待；
- 某些新的对象会在深挖过程中被补充进来。

我希望这些变化尽量直接回写到原有中间对象中，而不是完全散落到新的独立文档里。换句话说，第一阶段生成的表格，不只是筛选结果，也是后续持续演化的“工作底稿”。

在这一层，我希望统一增加两列，作为第二阶段对主表的标准化更新入口：

- `第二阶段操作`（填充：删除、深入等等）
- `第二阶段理由`（用自然语言描述前一列第二阶段操作的理由）

这样做的目的是把“对象为什么被降级、为什么被删掉、为什么被继续深挖”明确记录下来，而不是只保留最终状态，避免中途判断再次丢失。

### 4.3 第三阶段：形成洞察与写作辅助信息

第三阶段并不意味着一定要给出完全确定的工程建议，而是要在已有证据和初判基础上，形成更适合后续报告写作与问题归并的洞察性信息。

这里至少包含两类内容：

1. 面向开发人员的判断：某些问题在哪一层更可疑、哪些对象应优先处理、哪些异常更像共享链路问题而不是单点问题。
2. 面向写报告的判断：哪些对象应该放在一起讲、哪些问题之间存在上下游关系、哪些现象需要合并叙述，哪些则应拆开表达，避免混淆。

我特别强调一点：如果没有足够把握，就不要把某条意见写成过于确定的建议。第三阶段的价值，不在于强行自动化地下结论，而在于把证据、对象、关系和表达视角组织得更合理。

## 5. 我对“重要对象”的理解，以及 adapter 应如何支撑这种理解

在我当前的设想中，当我对系统本身还不够了解时，最容易让人信服、也最直接的方式，就是先把重要对象拉出来，给出它们的清单，并按若干启发性原则进行排序。

这些启发性原则可以包括：

- 平均响应时间；
- 错误率；
- 调用次数；
- 总体耗时；
- 慢调用次数；
- 其他能够反映风险、影响面或异常密度的指标。

这种方式有几个特点：

1. 它不依赖我一开始就对业务有很深的背景知识。
2. 它可以快速形成一个“从哪里看起”的入口。
3. 它天然适合作为中间表格和最终报告表格的共同基础。
4. 它有助于把“对象的重要性”从模糊判断，转成可解释、可排序、可复核的形式。

因此，adapter 至少要支撑我产出这样一种东西：**按一定启发性原则排序的重要对象清单，以及这些对象的关键运行参数。**

## 6. 中间数据对象的要求

我已经明确意识到，中间数据对象将贯穿整个流程，而且会被频繁修改。因此，它们的设计不能只是“临时导出一下就算了”，而需要同时满足以下几个目标。

### 6.1 数量受控

中间对象不能太多，否则不仅模型看不完，人也看不完。我希望控制中间文件与表格的数量，让人可以真正理解、修改和复核，而不是被大量碎片化结果淹没。

### 6.2 结构可演化

这些中间对象不是只为某一个阶段服务，它们会在不同阶段不断被补充。因此结构上需要允许：

- 初筛阶段先填写少量关键字段；
- 深挖阶段逐步补证据、补状态、补关系；
- 写作前阶段再补写作建议、归并建议或证据占位信息。

### 6.3 既适合机器处理，也适合人工阅读

我希望区分两类需求：

- 一类是便于脚本排序、过滤、更新和合并的机器友好结构；
- 一类是便于人工快速浏览和写进报告的阅读友好结构。

在这个取舍上，我当前更明确地倾向于：**表格是主对象，因为阅读起来更友好。**

这意味着：

- 表格是我在流程中频繁操纵、更新和查看的主要载体；
- JSON 可以作为补充证据、明细附属结构或挂接信息存在；
- 但在主线流程里，表格应该承担主要的工作底稿角色。

## 7. Adapter 应生成和维护的中间产物类型

从我的整体设想来看，adapter 及其下游配套脚本，最终至少要生成和维护以下几类中间产物。

### 7.1 各类对象的主表

这是整个流程里最核心的中间对象。它们既是第一阶段筛选结果，也是第二阶段持续更新的工作底稿，同时还能在最终报告中直接转化为表格素材。

这些主表至少应承担以下功能：

- 承载对象清单；
- 承载关键运行参数；
- 支撑启发式排序；
- 记录对象的重要程度；
- 记录第二阶段操作与理由；
- 记录证据、关系与后续写作线索。

### 7.2 深挖过程产生的附属证据

当我围绕某个接口、SQL 或其他对象继续深挖时，会拿到一些更细的材料，例如：

- 典型 trace；
- 页面 URL；
- 关联依赖；
- 调用链局部信息；
- 某些能说明问题的上下文片段；
- 为后续截图而准备的说明信息。

这类内容不一定适合都塞进主表，但必须和主表中的具体对象建立稳定关联，否则后面写报告时就会重新散落。

### 7.3 写作辅助信息

在第三阶段形成的洞察性内容，也应该以可落盘的方式保留下来。它既可以是主表中的附加字段，也可以是附属说明文件，但无论如何，都应该和对象主表之间存在明确关系。

这类信息可能包括：

- 某几个对象适合合并叙述；
- 某些问题疑似属于同一个问题簇；
- 某些异常更像共享链路故障而不是单点问题；
- 某些建议暂时没有足够把握，因此不应写成确定结论。

## 8. 证据沉淀与截图占位

我已经明确提出，后续写报告不仅需要结论和表格，还需要可回查的证据。这里有两个关键点。

### 8.1 证据必须可反向核验

落盘的证据不能只是模型的一段描述，而必须让我在之后能够反向验查，知道它来自哪里、如何再次打开、对应的是哪一个对象、哪一条 trace、哪一个依赖或哪一个页面入口。

因此，证据本身至少应满足：

- 能定位到具体对象；
- 能说明其与当前问题之间的关系；
- 能被后续人工复核；
- 能支撑正式报告中的论断，而不仅仅是作为“看过了”的痕迹。

### 8.2 图片未必由系统直接生成，但至少要有截图位与取证路径

当前阶段我不一定能够直接从听云网页端自动截图，因此这件事很可能需要人工完成。但即便如此，也不能因此让“图片证据”完全脱离流程。

更合理的做法是：

- 在分析过程中保留能够打开对应对象页面的 URL；
- 在需要写报告的位置预留图片占位；
- 在占位旁说明“应从哪个 URL 打开什么页面、截取什么内容、用来说明什么问题”。

这样一来，即使图片不是自动生成的，证据链也仍然是完整的。

> 待确认：后续是否要把截图占位也标准化，例如统一成“截图目的 / 页面 URL / 建议截图区域 / 说明对象 / 用途说明”这类固定模板。

## 9. Adapter 侧的非功能性要求

除了功能本身，我对 adapter 还有一些明显的非功能性要求。

### 9.1 要有清晰的层次与职责边界

adapter 至少要覆盖以下几层工作：

1. 帮助识别哪些对象值得纳入考虑；
2. 围绕这些对象做更深入的深挖；
3. 进一步分析对象之间的关系、成因与全局性背景；
4. 把前面得到的信息转成更适合写报告和复用的输出形式。

### 9.2 要尽量减轻对听云平台的压力

我非常在意对平台调用压力的控制，尤其是那些高频、重量级的 pack 或调用链路，不应该简单粗暴地整段抓出来，只为了在其中找一个局部对象。

这意味着 adapter 的职责之一，就是识别哪些调用代价高、哪些字段真正必要、哪些深挖动作需要更审慎地触发。它不只是一个“功能够不够”的问题，也包括“调用代价是否可接受”的问题。

### 9.3 字段与输出表达要逐步统一

平台原始返回的信息很多，但并不是所有字段都值得保留到最终的 pack 中。很多字段可能只在某一层有意义，而在另一层只是噪音。

因此，需要逐步统一：

- 哪些字段保留；
- 哪些字段只用于内部处理；
- 哪些字段要进入对开发友好的输出；
- 哪些字段要转成更统一、更具语义的表达。

## 10. 我希望继续保留的 adapter 相关文档

围绕 adapter 这一层，我认为不能只保留代码，还需要同步沉淀文档，包括但不限于：

### 10.1 整体架构与工作流文档

说明 adapter 在整个项目里处在什么位置，如何与 capture、client、报告产物衔接。

### 10.2 分层与模块职责文档

说明每个 pack、每个 adapter、每个模块分别负责什么，边界在哪里，对应请求链路的哪一段。

### 10.3 开发过程记录

记录一些取舍、阶段性判断、能力边界和已知缺口，避免后续再次回到“靠记忆推进”。

当前仓库已经有一些方向相近的文档和产物，例如：

- 当前 adapter 主设计文档
- 历史阶段设计快照
- 历史经验文档
- 样例 `report_bundle`

这些方向和我现在对 adapter 的定位是相匹配的，说明目前的文件化沉淀方向本身没有跑偏。

## 11. 这份文档的作用

这份文档的作用，不是直接把 adapter 的所有实现细节写死，而是先把我当前对 adapter 的整体理解压实下来：

- 它不是平台代理，而是诊断中间层；
- 它既服务于对象发现，也服务于对象深挖；
- 它既服务于中间表格的持续更新，也服务于后续证据沉淀和写报告；
- 它最终要输出的，不是零散数据，而是可筛选、可更新、可引用、可回查的中间产物体系。

后续无论我是继续设计 pack、细化主表字段、补充证据结构，还是优化对平台压力的控制，都应该围绕这条主线来推进。
