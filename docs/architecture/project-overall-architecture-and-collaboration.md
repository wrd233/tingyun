# 听云项目整体架构与协作说明（整理稿）

> 本文档是当前项目整体架构与协作方式的主设计文档。

## 1. 文档定位

这份文档聚焦于项目整体架构，不展开具体实施计划，也不直接给出局部优化建议，而是把当前项目在顶层上的组成方式、协作关系、职责边界和整体工作流整理清楚。我的目标是先把整个项目从上往下讲明白：系统由哪几部分组成、它们之间如何配合、各自承担什么职责，以及为什么要这样分层。

本文的处理原则如下：

- 尽量保持我原本的想法不变，只做结构化整理与语言润色。
- 在我有把握的地方做少量扩充，使整体链路更完整、更便于后续继续拆模块。
- 统一把表述改为我的视角，而不是面向外部讲解的“你”的视角。
- 对于仍然需要继续确认的地方，不在这里展开问题清单，而是以内嵌引用的方式保留下来，便于后续逐段确认。

## 2. 当前项目的根本目标

我做这整套工作的根本目的，不是为了“抓更多接口”或“沉淀更多材料”本身，而是为了能够向开发人员给出尽可能明确、可验证、可执行的判断：

1. 当前系统到底发生了什么。
2. 哪些问题最值得关注。
3. 这些问题背后的可能成因或根因是什么。
4. 哪些调整方向是可以考虑的。
5. 这些调整的优先级大致如何排序。

因此，这个项目的核心，不是单纯的数据获取，而是围绕“对象—证据—判断—表达”形成一条稳定链路。前面的抓取、整理、筛选、深挖，最终都要服务于后面的工程表达：让报告中的内容既能让负责人快速把握重点，也能让研发和运维拿去定位与整改。

## 3. 我当前对整体架构的三段式理解

如果从我当前真正想要推动的工作流来理解，而不是只看仓库目录，那么整个项目更适合被归纳为三大部分。它们不是彼此孤立的功能块，而是首尾衔接、逐层收束的一条链路。

### 3.1 第一部分：能力供给与数据抽取侧

这一部分的职责，是和听云 APM 平台真实对接，把平台原始能力转成我后续能够稳定消费的能力来源。它对应的是机器 A 这一侧的能力基础，核心价值不在于“原样镜像平台”，而在于：

- 对接听云平台原始接口。
- 识别并沉淀真实可用的诊断链路。
- 把平台能力整理成更适合分析、诊断和报告消费的中间表达。
- 尽量避免调用方直接面对平台接口的复杂性、页面逻辑和字段噪音。
- 对高频、重量级调用做必要收束和控制，降低对听云平台本身的压力。

如果从当前仓库的已有结构来看，这一部分主要体现在两块基础上：

1. `tingyun_cdp_capture`：负责抓取听云页面触发的 `/server-api/` 请求，并对关键诊断链路做回放与样本沉淀。
2. `tingyun_adapter`：负责把听云原始接口整理成更适合分析、诊断和报告消费的结构化 pack。

也就是说，这一部分并不是纯抓取，而是“抓取 + 归一 + 面向后续分析的能力重组”。

### 3.2 第二部分：远程消费、对象收束与素材生产侧

这一部分对应的是机器 B 侧和 agent 侧的工作。它的任务不是重新发明抓取逻辑，而是基于第一部分已经供给出来的能力，去组织具体分析工作流，生成足够可复用的素材。

这一层至少承担以下职责：

- 通过 client 稳定地远程调用机器 A 上的 adapter。
- 让 Codex、ChatGPT 或其他 agent 不再直接面对平台原始接口，而是消费更稳定的 pack。
- 基于这些能力先做“宽入口发现”，找出值得进一步观察的重要对象。
- 对初步收束出的对象继续深挖，寻找其典型 trace、拓扑关系、根因线索和潜在关联。
- 把分析过程中不断产生的新信息回写到中间对象中，而不是让信息散落在零碎文本里。
- 最终为后续写报告准备结构化、可复核、可回查的素材。

这一部分在当前仓库中主要对应：

- `tingyun_adapter_client`：运行在机器 B，通过 HTTP 调用机器 A 上的 adapter 服务，使本机 agent、Codex 或其他模型可以稳定消费这些 pack。
- 一系列围绕中间表格、证据索引、写作输入、候选对象清单而形成的导出与组织逻辑。

这意味着我当前的主线已经比较明确：不是让模型直接去“想办法看平台”，而是让模型通过一层经过整理的 client/adapter 能力来工作，再把得到的结果沉淀成可持续更新的素材。

### 3.3 第三部分：成文、归档与正式交付侧

第三部分是最终面向交付的部分。它并不只是“生成一份报告正文”，而是把前两部分沉淀下来的对象清单、证据链、排序结果、归并判断和写作线索，组织成可正式交付的表达。

这一部分要承接的内容包括：

- 正式调研/巡检报告。
- Excel、CSV、JSON 等辅助材料。
- 可用于复核和回查的证据索引。
- 对象清单、问题矩阵、写作输入材料等文件化产物。

从当前仓库来看，这一部分已经在样例报告包中有比较明显的雏形，例如 `samples/monitored_systems/bizsystem_1065/2026-04-monthly-diagnostic-sample/report_bundle/` 下包括：

- `01_exec_summary.md`
- `02_writer_input.md`
- `03_issue_matrix.csv`
- `04_evidence_index.csv`
- `05_review_bundle.json`

这说明我现在要做的，并不是从零开始设计“报告产物长什么样”，而是继续把这些已经出现的产物往更完整、更稳定的方向推进。

## 4. 三大部分之间的协作关系

我现在希望建立的，不是一个“抓完数据直接丢给大模型写报告”的松散流程，而是一条职责逐层明确、产物逐层收束、信息逐层增值的链路。

### 4.1 第一部分向第二部分提供什么

第一部分并不直接生产最终报告内容，它首先要生产的是“能力”与“结构化原材料”。也就是说，它要提供的不是平台原始返回本身，而是更适合后续分析消费的 pack、对象视图、访问入口、证据线索和必要字段。

第二部分基于这些能力，才能进行：

- 候选对象筛选；
- 启发式排序；
- 重点对象深挖；
- 证据挂接；
- 对象关系识别；
- 中间对象持续更新。

如果第一部分做得不够好，那么第二部分就会被迫重新处理平台细节，导致 agent 浪费大量 token，也会使整个工作流变重、变碎、难以稳定。

### 4.2 第二部分向第三部分提供什么

第二部分最重要的任务，是把“原材料”变成“写报告真的能用的素材”。我并不希望报告写作阶段还在从头做筛选、做推理、做对象对齐，那样会让最终成文阶段承担过多不稳定工作。

因此，第二部分需要输出的，应该是：

- 已经经过筛选和排序的重要对象清单；
- 带有关键运行参数的主表；
- 已经挂接证据的候选对象；
- 对象之间可能的关联关系；
- 某些有把握的初步判断；
- 适合写报告时直接引用或改写的素材。

也就是说，第三部分最理想的状态，不是“重新分析”，而是“基于已组织好的素材进行正式表达”。

### 4.3 第三部分如何反向约束前两部分

虽然第三部分在链路的最后，但它会反过来约束前面两部分。我之所以这么强调最终交付物的形态，是因为报告中要写什么、怎么写、哪些内容能被接受，本身就决定了前面应该怎样取数、怎样组织中间产物。

例如：

- 报告需要写检测范围和对象边界，那么前面就必须保留足够清晰的资产与范围信息。
- 报告需要用表格说明重点接口和 SQL，那么前面就必须生成可排序、可复用的对象主表。
- 报告需要体现证据链，那么前面就必须沉淀可反向核验的 URL、trace 入口和截图提示。
- 报告需要减少 AI 味、增强可执行性，那么前面就要尽量把对象、证据、归因线索组织好，而不是把大量半成品问题留给写作阶段。

因此，整个项目不是“前面分析、后面写作”这么简单，而是“后面的表达要求反过来塑造前面的能力形态”。

## 5. 我当前设想的整体工作流

### 5.1 机器 A：adapter 所在端

机器 A 负责运行 adapter 相关代码，并与听云 APM 平台交互。它不是一个简单的数据转发层，而是一个面向分析和报告的中间能力层。

这一侧的核心职责包括：

- 对接听云平台原始接口；
- 把平台能力组织成更适合诊断和报告的中间表达；
- 尽量避免调用方直接面对平台接口的复杂性与页面逻辑；
- 对高频、重量级的调用做必要控制，降低对听云平台本身的压力。

### 5.2 机器 B：远程调用与素材生产端

机器 B 负责运行 client，以及 Codex 等 agent，通过远程调用机器 A 上的 adapter 获取素材。这样做的好处在于：

- 听云 token、真实调用能力与配置集中在机器 A 管理；
- 机器 B 更稳定地面向结构化 pack，而不是原始平台调用；
- 后续可以让 ChatGPT、Codex 或其他工具共享同一套中间能力，而不是重复建立抓取逻辑。

### 5.3 素材生产与正式写作的分流

在素材已经形成之后，我当前考虑保留两条写作路径：

1. 将素材输入给 ChatGPT，直接整合成 Word 文档。
2. 继续使用 Codex 等 agent，把素材汇总成 LaTeX 格式报告，再尝试导出为 Word 或 PDF。

这里真正的关注点，不只是“用哪个工具写”，而是：

- 文字风格能否减少明显的 AI 味；
- 报告格式能否更稳定；
- 中间材料与最终成文之间的映射能否更可控；
- Word 是否仍然是必须满足的正式交付形态。

> 待确认：LaTeX 在这里更像一个中间过渡层，用来稳定格式、降低文字漂移；最终我仍然需要 Word 或 PDF，且优先选择 Word。

## 6. 为什么我要先做顶层梳理

结合我目前的推进方向，我最优先想做的，其实不是立刻细抠某一个 pack 的实现，而是先对整个项目做一次自顶向下的结构校准。

我希望先明确：

- 整个项目的顶层分层到底是什么；
- 各部分之间的职责边界是否清楚；
- 当前仓库中的组织方式与我真正想要的结构之间，哪些是一致的，哪些存在出入；
- 哪些模块可能存在职责混杂、命名不清或代码冗余；
- 哪些地方需要先在概念和文档层面统一，再进入局部优化。

换句话说，我现在真正想先完成的，是一次“项目结构与思想框架的校准”。只有在这个顶层框架比较明确之后，后面聚焦到一个个具体模块时，优化才不容易跑偏。

## 7. 开发过程中需要同步保留的文档

从我当前的理解来看，代码之外，文档本身也是项目成果的一部分，而且不应该等到最后再补。

至少需要持续保留以下几类文档：

### 7.1 整体工作流与项目架构文档

需要有一份从顶层说明整个项目是怎么流转的文档，说明：

- 各层分别负责什么；
- 它们的边界在哪里；
- 输入输出分别是什么；
- 它们之间是怎样串起来的。

### 7.2 分层与模块职责文档

不仅要讲“有哪几个项目”，还要讲清楚每个层次、每个模块、每个 pack、每个 adapter 的职责与边界，以及它们分别对应到请求链路的哪一部分。

### 7.3 开发过程记录

开发过程中的一些取舍、阶段性理解、能力边界、已知缺口，也需要同步记录。否则项目虽然在变复杂，但很多关键判断会再次散失，后续又会回到“靠记忆和临时沟通推进”的状态。

当前仓库中已经存在一批类似以下方向的文档和产物：

- 当前主设计文档
- 历史阶段交付文档
- 样例 `report_bundle`
- 历史经验与复盘文档

这说明“架构理解、能力边界、写作输入、证据索引、复核材料”已经开始被逐步文件化，这个方向本身是正确的。

## 8. 这份架构稿的作用

这份文档的作用，不是替代具体模块设计，也不是直接把每一个 pack 的输入输出细节都写死，而是先把我当前对整个项目的总体理解压实下来：

- 第一部分负责能力供给与数据抽取；
- 第二部分负责远程消费、对象收束与素材生产；
- 第三部分负责成文、归档与正式交付。

这三部分共同组成一条从平台能力到正式报告的完整链路。后续无论我是继续拆 adapter、整理中间对象、设计导出结构，还是优化最终写作路径，都应该回到这条主线上来检查：它是否真的有助于我更稳定地回答开发人员最关心的问题——系统发生了什么、为什么重要、根因可能是什么、优先要改什么。
