# tingyun 仓库重构目标状态说明（多系统 / 多批次版）

> 版本：2026-04-12  
> 文档定位：本文件用于描述 `wrd233/tingyun` 仓库在重构完成之后应当呈现出的目标状态。本文不采用阶段推进或分步执行的写法，而是直接说明重构完成后仓库应该如何分层、各目录承担什么职责、哪些内容应被保留、哪些内容应被迁移、哪些内容只应作为本地产物存在，以及这些结构如何与我当前的分析工作流、adapter 中间产物和最终交付物保持一致。

---

## 1. 本次重构要解决的核心问题

当前仓库已经具备明确主干，但仍然同时带有较强的“开发工作台”特征。代码工程、阶段文档、样例输出、运行副产物、临时调试结果和历史材料还没有被完全拉开边界。这会带来几个直接问题：

1. 主干工程与运行产物混杂，导致仓库语义不纯。
2. 文档与代码目录混杂，导致协作者无法快速判断某个目录到底是“运行入口”还是“历史说明”。
3. 报告相关概念已经出现，但边界尚未完全固定，容易让后续 agent 误解 `pack`、`writer input`、`sample bundle`、`final report` 之间的关系。
4. adapter 已经不仅仅是一个取数层，而是在承担候选对象筛选、证据组织、深挖支撑和报告素材导出等职责；如果仓库结构仍然停留在早期状态，会不断放大后续维护成本。
5. 当下一次 Codex 或其他 agent 阅读仓库时，如果看不清目录职责，就很难稳定地接续工作，也很难在正确的位置继续补代码、补文档或补样例。
6. 当前仓库对“多个待监测系统”和“同一系统多个监测批次”的支持语义还不够明确，容易把跨系统资料、同系统历史批次结果和本次运行产物混在一起。

因此，这次重构的本质不是“重写实现”，而是把仓库整理成一个**分层明确、语义清楚、文档同步、产物受控、支持多系统 / 多批次运行、便于 agent 接续理解和持续演进**的工程仓库。

这个方向与我前面已经明确的几件事情保持一致：

- 仓库整体要围绕三大主工程协作展开。
- adapter 要围绕中间对象、证据和报告素材输出组织能力。
- 最终交付物要反过来约束前面的目录、命名和导出形态。
- 同一个仓库要能同时服务多个待监测系统，也要能承载同一系统多次监测的结果复用与隔离。

## 2. 重构完成后的整体解释方式

重构完成后，我会把整个仓库解释为：**三个主工程 + 五类支撑目录 + 一套统一的多系统 / 多批次运行语义**。

### 2.1 三个主工程

#### （1）`tingyun_cdp_capture/`

这一部分负责抓取、样本沉淀和链路回放，用于确认听云平台真实可用的接口能力、页面行为和取证入口。它是整个项目最靠近平台的一层，但它本身不直接面向最终报告写作，而是为 adapter 提供可靠的上游理解基础。

#### （2）`tingyun_adapter/`

这一部分是核心中间层。它不是简单地镜像听云原始接口，而是把平台能力重新组织成更适合候选对象筛选、对象深挖、证据组织、关系补充和报告消费的 pack 与导出视图。adapter 是整个项目里最重要的结构中心。

#### （3）`tingyun_adapter_client/`

这一部分运行在机器 B，负责远程调用机器 A 上的 adapter 服务，并把 adapter 暴露出来的导出能力物化为本地可浏览、可交付、可继续加工的材料目录。它承担“远程消费”和“本地物化”的角色，但不承担平台抓取，也不承担最终报告的唯一写作职责。

### 2.2 五类支撑目录

除上述三个主工程外，仓库还需要若干支撑目录，它们不属于主工程本身，但会长期存在并为主工程服务：

- `reference/`：长期参考资料、平台手册、模板、取证指南。
- `docs/`：整体架构、模块边界、工作流说明、报告经验、关键决策等统一文档区。
- `samples/`：需要随仓库长期保留、供阅读和回归参考的样例输出。
- `knowledge/`：需要被长期保存并被 adapter 或分析流程读取的手工映射、业务上下文、review 队列等知识文件。
- `artifacts/`：只作为本地运行产物工作区存在，默认不入库。

### 2.3 统一的多系统 / 多批次运行语义

重构完成后，仓库中的“系统”和“批次”不再只是文件名中的隐式概念，而是被提升为明确的路径语义：

- **系统（system）**：表示一个待监测的业务系统或被观测对象集合。
- **批次（batch）**：表示某个系统在某一次监测、巡检、诊断或专项排查中的独立运行上下文。

一个系统可以有多个批次；多个批次之间可以共享系统级知识，但运行产物、证据、主表和报告材料必须按批次隔离。这样既能复用上一次监测的沉淀，也能在需要时明确启动一个全新的批次，而不会污染历史结果。

5. 多系统和多批次的组织方式在路径上是显式的，而不是仅依赖日期、临时命名或操作者记忆来区分。

## 4. 三个主工程之间的协作关系

### 4.1 从平台到报告素材的主链路

重构完成后，仓库中的三大工程之间应被清楚理解为以下协作关系：

1. `tingyun_cdp_capture/` 负责建立对平台真实接口链路和页面行为的把握。
2. `tingyun_adapter/` 基于这种把握，把原始能力重新组织为适合对象筛选、对象深挖、证据组织和报告消费的中间能力。
3. `tingyun_adapter_client/` 在机器 B 上消费 adapter 暴露出来的能力，把中间能力物化为可以直接交给模型、写作者或后续脚本使用的本地材料目录。

这三者之间不是平行关系，而是一个逐层收束的链路：

- capture 保证“来源可信、能力真实”；
- adapter 保证“结构清晰、表达友好、证据可连回原始对象”；
- client 保证“远程可消费、本地可落地、写作可接续”。

### 4.2 三个主工程之间的职责边界

为了防止目录继续膨胀，重构后的职责边界需要写得非常清楚。

#### `tingyun_cdp_capture/` 不承担的事情

- 不直接承担最终报告写作。
- 不承担报告对象主表的长期维护。
- 不承担 client 侧物化目录的组织。
- 不承担按系统 / 批次汇总后的最终材料归档。

#### `tingyun_adapter/` 不承担的事情

- 不退化为简单平台代理或原始接口透传层。
- 不把所有临时分析结果直接堆放到项目根目录。
- 不把阶段文档和代码长期混放在一起。
- 不把某个具体系统或某个具体批次的本地运行结果直接固化在源码目录中。

#### `tingyun_adapter_client/` 不承担的事情

- 不替代 capture。
- 不长期兼任示例报告仓或历史交付物堆栈。
- 不承担最终报告唯一成文路径的定义权。
- 不在源码工程中长期保存任意系统的真实运行产物。

### 4.3 机器 A / 机器 B 语义在仓库中的对应关系

重构完成后，仓库中的机器语义也应与目录语义保持一致：

- 机器 A 主要对应 `tingyun_adapter/` 所在服务能力，以及它向平台发起的能力调用。
- 机器 B 主要对应 `tingyun_adapter_client/` 所在消费与物化能力，以及其上运行的 agent、Codex、ChatGPT 前置整理逻辑等。
- `tingyun_cdp_capture/` 既服务于平台理解，也服务于 adapter 能力边界确认，但不等同于日常报告生成链路中的每次调用入口。

## 5. 多系统 / 多批次的统一结构语义

这是这次重构中需要额外补齐的一层，因为它会直接影响目录设计、命名规则、中间产物管理和文档说明方式。

### 5.1 系统级语义

系统级目录用于承载**跨批次稳定存在**的内容。它的重点不是某一次运行，而是该系统本身长期成立的上下文，例如：

- 系统基本信息与别名；
- 资产范围与边界说明；
- 手工维护的组件映射；
- 业务背景、命名映射、对象归一规则；
- 长期积累的 review 队列或待确认问题；
- 某些希望在下一次诊断时继续复用的知识文件。

这些内容适合放在：

```text
knowledge/monitored_systems/<system_key>/
```

### 5.2 批次级语义

批次级目录用于承载**某一次具体监测或诊断活动**的运行结果。它的重点是隔离本次分析上下文，防止与历史批次混淆。典型内容包括：

- 本次抓取样本；
- 本次 pack 导出结果；
- 本次候选对象主表；
- 本次证据索引；
- 本次诊断 markdown；
- 本次报告材料与报告正文；
- 本次过程中生成的调试文件。

这些内容适合放在：

```text
artifacts/monitored_systems/<system_key>/<batch_key>/
```

### 5.3 系统级与批次级之间的关系

重构完成后，整个仓库需要明确支持两种工作方式：

#### （1）复用上次监测沉淀

当同一个系统再次做监测时，我可以复用该系统在 `knowledge/` 下长期保留的资料，也可以在新批次中复用历史批次的一部分主表、映射、证据入口或写作线索。但复用动作应发生在批次目录之内，不能直接让历史批次和本次批次共用同一份运行文件。

#### （2）启动全新监测批次

如果我希望完全重新开始，则可以直接创建一个新的 `<batch_key>`，只继承系统级最小背景信息，而不继承任何旧批次运行结果。这样能保证新一轮诊断不会被旧结果污染。

### 5.4 建议的命名语义

为了让 agent 也能稳定理解，系统和批次的命名需要可解析：

- `system_key`：应是稳定、可读、去空格、适合进入路径的系统标识，例如 `bizsystem_1065`、`nb_mobile_legal_affairs`。
- `batch_key`：应体现监测批次的独立身份，建议至少包含日期或时间范围，例如 `2026-04-monthly-check`、`2026-04-12-special-slow-api`。

这样一来，目录本身就具备可读性，不需要先打开文件才能知道“这是哪个系统、哪一批次的材料”。

## 6. 重构完成后的 `tingyun_cdp_capture/` 目标状态

### 6.1 定位

`tingyun_cdp_capture/` 在重构后应当被明确解释为：**平台行为抓取、接口样本沉淀与关键链路回放工程**。

### 6.2 应长期保留的内容

该目录内应当只保留与“运行 capture 工程”直接相关的内容，例如：

- 抓取脚本；
- 回放脚本；
- 最小测试；
- 本地配置样例；
- 工程自身的 README；
- 该工程自身需要的最小文档入口。

### 6.3 应退出主路径的内容

以下内容不应继续在该工程主路径中长期混放：

- 大体量原始抓取目录；
- 持续膨胀的 raw logs；
- 一次性分析 markdown；
- 偏全局性的架构说明、写报告经验和历史阶段总结；
- 某个具体系统、具体批次的真实运行产物。

### 6.4 与文档区、样例区和产物区的关系

- 如果某些抓取样本是“最小可复现样本”，可以以 sample 形式被缩样后保留。
- 如果某些说明已经超出“如何运行 capture”，就应进入 `docs/` 而不是继续停留在 capture 根目录。
- 如果某些结果只是本地运行产物，则应进入 `artifacts/` 并被忽略。

重构完成后，任何 agent 阅读 `tingyun_cdp_capture/` 时，都应该能立刻判断：这里是抓取与回放工程，而不是“杂项资料堆”。

## 7. 重构完成后的 `tingyun_adapter/` 目标状态

### 7.1 定位

`tingyun_adapter/` 在重构后应当被明确解释为：**整个项目的核心中间层与结构中心**。它的价值不在于“把听云接口调出来”，而在于把平台能力改造成更适合筛选重要对象、深挖对象根因、组织证据、生成导出视图和支撑报告写作的中间能力。

### 7.2 adapter 对整体工作流的覆盖面

adapter 需要覆盖我当前工作流中的三类核心任务：

1. 帮助确定哪些对象值得纳入观察；
2. 围绕这些对象提供进一步深挖与证据补充能力；
3. 把前两步得到的结果整理为适合后续写报告和人工复核的输出。

也就是说，adapter 既要支撑“我该看谁”，也要支撑“为什么看它”，还要支撑“我最后如何把它写出来”。

### 7.3 adapter 生成的中间对象应当如何存在

结合我已经明确的设计思路，重构完成后 adapter 生成的中间对象应当遵循以下原则。

#### （1）表格是主对象

我的主对象仍然是表格，而不是 JSON。原因很直接：表格更利于阅读、排序、筛选、人工复核和最后进入报告。

#### （2）每一类对象各有一张主表

我不采用一个统一候选池主表来承载所有类型对象，而是采用“每一类对象各一张主表”的方式。接口是一张主表，SQL 是一张主表，未来如果扩展到其他对象类型，也应各有各的主表。

#### （3）表格贯穿全流程并持续更新

这些主表不是一次性导出物，而是贯穿整个流程的工作底稿。它们在不同阶段会被持续更新：

- 第一阶段填入全量候选对象及其初筛指标；
- 第二阶段补入操作状态、重要程度、自然语言理由、关联对象、典型证据等；
- 第三阶段进一步补入归并视角、写作提示和可写入报告的稳定判断。

#### （4）第二阶段状态更新必须显式保留

主表中需要显式保留第二阶段操作与理由，例如：

- `第二阶段操作`：删除、深入、保留观察、合并观察等；
- `第二阶段理由`：用自然语言说明该操作的依据。

这样做的目的是保留对象演化痕迹，而不是只留下最后结果。

#### （5）JSON 作为补充证据而不是主对象

JSON、trace 明细、依赖细节、页面链接、截图提示等内容仍然需要保留，但它们的角色是表格的补充证据，而不是替代表格成为主阅读入口。

### 7.4 adapter 输出层的解释方式

重构完成后，adapter 相关输出在语义上应当稳定为以下层次：

1. **pack**：adapter 内部返回的结构化对象；
2. **writer input**：面向写作者或模型的单入口写作输入；
3. **export view**：pack 中声明的固定导出视图；
4. **materialized report pack**：由 client 将 export view 物化到本地目录后的结果；
5. **sample bundle**：为了示例和演示长期保留的样例报告包；
6. **final report**：最终交付给人的报告正文。

这几个层次在重构完成后不能再混用名称，也不能继续把不同层次的对象散落到不同目录里而没有统一解释。

### 7.5 adapter 与多系统 / 多批次的关系

adapter 本身不应把某个系统、某个批次写死在源码目录里，但它需要显式支持以下语义：

- 输入参数中能够传入 `system_key` 与 `batch_key`；
- 输出的 pack、writer input、export view 能够带上系统和批次上下文；
- 需要复用系统级知识时，能读取 `knowledge/monitored_systems/<system_key>/` 下的内容；
- 需要落地本次运行材料时，由 client 将其物化到 `artifacts/monitored_systems/<system_key>/<batch_key>/` 下。

换句话说，adapter 负责理解“这是哪个系统、哪一批次、可以读哪些长期知识、正在生成哪一批次的中间材料”，但它不直接把本地目录管理和最终归档职责吞进源码内部。

### 7.6 adapter 内部目录边界

重构完成后，`tingyun_adapter/src/tingyun_adapter/` 仍然可以保留现有大方向合理的目录，例如：

- `clients/`
- `config/`
- `domain/`
- `invocation/`
- `normalizers/`
- `service/`
- `sources/`

但 `usecases/` 不应继续以“越来越厚的总装配层”方式被理解。即便暂时不做物理拆分，文档上也必须明确其职责分组，例如：

- candidate 构建；
- component 构建；
- evidence enhancement；
- export materialization support；
- report support；
- knowledge enhancement。

后续 agent 一旦进入这个目录，应能够立刻知道每一类文件属于哪一层职责，而不是从文件名猜测。

---

## 8. 重构完成后的 `tingyun_adapter_client/` 目标状态

### 8.1 定位

`tingyun_adapter_client/` 在重构后应当被明确解释为：**远程调用器 + 本地物化器**。

它的职责是：

- 调用机器 A 上的 adapter 服务；
- 获取 pack 或 export view；
- 按约定路径把结果物化到本地材料目录；
- 为 agent、写作者和后续脚本提供稳定的落盘入口。

### 8.2 它不再承担的事情

重构完成后，client 不应继续承担以下职责：

- 在源码目录里长期保存报告样例；
- 在 `reports/` 下积累越来越多的真实报告结果；
- 同时兼任最终报告仓、样例仓和运行产物仓。

### 8.3 client 与本地材料目录的关系

client 的核心职责之一，是把 adapter 的输出物化为**按系统 / 批次隔离**的本地材料目录。也就是说，它落盘时应以如下结构为默认目标：

```text
artifacts/monitored_systems/<system_key>/<batch_key>/
```

而不是：

- 直接在 `tingyun_adapter_client/` 根目录生成报告；
- 直接在仓库根目录生成一批日期化文件；
- 把不同系统或不同批次的结果混放在一起。

### 8.4 client 与样例的关系

如果我希望保留某份结果作为示例，则应从某个具体批次的材料中挑选出一个稳定子集，复制或整理到：

```text
samples/monitored_systems/<system_key>/<sample_batch_key>/
```

这意味着 sample 是**经过挑选和归位后的长期样例**，而不是把真实运行目录直接纳入版本库。

## 9. 重构完成后的 `reference/`、`docs/`、`samples/`、`knowledge/`、`artifacts/` 目标状态

### 9.1 `reference/`

`reference/` 只放长期参考资料，不放过程性产物。建议内部再区分为：

- `reference/manuals/`：平台手册、接口说明、外部参考资料；
- `reference/templates/`：报告模板、取证指南、格式模板。

### 9.2 `docs/`

`docs/` 是所有非代码但需要长期版本化文档的统一入口。重构完成后建议解释为：

- `docs/architecture/`：顶层架构、目录职责、模块边界、系统 / 批次语义、adapter 内部职责说明；
- `docs/workflows/`：跨机器协作流程、capture 运行方式、client 物化边界、监测批次流转说明；
- `docs/reporting/`：报告表达要求、产物解释、证据链规则、截图占位规则、样例说明；
- `docs/decisions/`：关键命名决策、目录语义决策、输出层次定义、是否保留某些旧概念的决策。

### 9.3 `samples/`

`samples/` 只放**需要长期保留并愿意入库的样例**。这些样例不是为了“保存一切”，而是为了：

- 给新 agent 一个最小可读示例；
- 给后续开发提供对照样本；
- 给 README 和文档提供实际示例。

样例也应按系统和批次组织，但样例批次可以是经过抽样和整理后的稳定版本，而不是完整复制所有真实产物。

### 9.4 `knowledge/`

`knowledge/` 用于存放系统级长期知识，而不是某次运行的瞬时结果。它的典型内容包括：

- 系统画像与别名；
- 组件或对象映射；
- 手工确认的业务上下文；
- 长期存在的 review 队列；
- 后续仍希望继续复用的命名、归一化和边界知识。

### 9.5 `artifacts/`

`artifacts/` 是本地运行产物工作区，默认不入库。它承担以下内容：

- 某一批次的抓取结果；
- 某一批次的 pack 导出；
- 某一批次的对象主表；
- 某一批次的证据、截图说明、诊断 markdown；
- 某一批次的 report materials 和最终报告。

这个目录的价值在于把所有“活的运行结果”收拢起来，同时保证它们不污染源码工程。

## 10. 重构完成后的报告输出语义

这部分必须在仓库中被明确写下来，因为它会影响目录、命名和文档。

### 10.1 统一解释方式

重构完成后，我会统一解释以下几个概念：

1. **pack**：adapter 内部返回的结构化对象；
2. **writer input**：供写作者或模型直接消费的单入口写作输入；
3. **export view**：pack 内声明的固定路径导出视图；
4. **materialized report pack**：client 将 export view 物化到本地目录后的结果；
5. **sample bundle**：为了说明结构和演示效果而长期保留的样例报告包；
6. **final report**：最终交付给人的报告正文。

### 10.2 与最终交付物的关系

最终交付物仍然不只是一篇报告，而是一套交付件：

- 正式报告正文；
- 对象清单与排序结果；
- 证据索引与回查入口；
- 必要的中间表格或附属材料；
- 便于复核和二次加工的结构化文件。

因此，仓库中的输出语义不能只围绕“生成一个 report.md”来设计，而必须围绕这整套交付件来设计。

### 10.3 与多系统 / 多批次的关系

这些输出在路径上也必须带有系统和批次语义。例如：

```text
artifacts/monitored_systems/<system_key>/<batch_key>/report_materials/
artifacts/monitored_systems/<system_key>/<batch_key>/reports/
```

这样才能确保我在面对多个系统、多个批次时，不会把不同上下文的 writer input、证据索引和报告正文混在一起。

## 12. 重构完成后的样例与真实产物边界

为了避免后续仓库再次膨胀，样例与真实产物的边界要在重构完成后被固定下来。

### 12.1 什么是样例

样例是指：

- 愿意长期保留；
- 愿意进入版本库；
- 用于说明结构、演示效果、帮助 agent 理解的有限材料。

### 12.2 什么是真实产物

真实产物是指：

- 某个具体系统某个具体批次运行出来的结果；
- 可能体量大、变动快、数量多；
- 主要用于当次分析、复核和写报告；
- 默认不应直接进入版本库。

### 12.3 边界规则

因此，重构完成后我要坚持以下边界：

- **样例进入 `samples/`，且必须是经过挑选和整理后的稳定子集。**
- **真实产物进入 `artifacts/`，默认不入库。**
- **源码工程目录只保留运行所需内容，不保留真实运行结果。**

---

## 13. 重构完成后的 `.gitignore` 语义

`.gitignore` 在重构完成后不只是技术细节，而是仓库边界的一部分。它需要清楚表达出以下几类东西默认不进入版本库：

- 本地配置；
- 临时调试文件；
- 缓存 markdown / json；
- zip 打包结果；
- egg-info 等打包副产物；
- 原始 capture 日志；
- `artifacts/` 下的批次产物；
- client 或 adapter 运行期间生成的本地 report materials。

这样一来，仓库边界不是靠操作者自觉，而是靠路径设计与忽略规则共同约束。

---

## 14. 重构完成后的整体效果

当这次重构完成后，我希望仓库达到如下状态：

1. 根目录只剩长期主干，不再出现 `.tmp_*`、日期化调试文件、临时 pack 结果和缓存文件。
2. 任意协作者打开仓库，都能一眼看出 capture / adapter / client 三大工程主线。
3. 文档、样例、知识、运行产物各归其位，不再互相挤占目录语义。
4. adapter 的中间对象、输出层次和最终交付物之间的关系在文档中被明确写清。
5. 多个待监测系统可以并存，同一系统的多个监测批次也可以并存，并且系统级知识与批次级产物边界清楚。
6. 需要复用上次监测结果时，我有明确的复用入口；需要重新开一批时，我也有明确的隔离入口。
7. 下一次 Codex 或其他 agent 进入仓库时，不需要先靠猜测理解结构，而是可以通过 README 和 docs 直接知道每个目录承担什么职责，以及应该把新的内容放在哪里。

## 15. 一句话总结

这次重构不应被理解为“重写仓库”，而应被理解为：**把已经逐渐成型的主干工程，从历史副产物、临时产物和混杂目录中解放出来，并且补上多系统 / 多批次运行所需的路径语义、文档语义和产物边界，使仓库从工作区形态转向可持续维护、可被 agent 稳定接续的工程形态。**
