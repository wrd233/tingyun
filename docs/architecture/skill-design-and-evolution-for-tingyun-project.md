# 听云项目 Skill 设计与演进说明

> 本文档是当前仓库中关于项目级 skill 体系的设计与演进说明。它解释为什么需要 `skills/`、当前 skill 处于什么阶段、经验应沉淀到哪里，以及后续如何继续把文档型 skill 强化为更稳定的工程资产。

## 1. 文档定位

这份文档用于系统整理当前项目中关于 skill 建立的思路。

这里讨论的重点不是某一个 prompt 怎么写，也不是直接给出某个脚本实现，而是把以下问题整理清楚：

- 为什么这个项目需要建立 skill；
- skill 能否先用自然语言来描述；
- 自然语言描述与可执行 skill 之间如何转化；
- 一个良好建设的 skill 应该包含哪些部分；
- 以当前项目为例，完整跑顺这套系统大致需要哪些 skill；
- 项目中的经验判断应如何沉淀到 skill；
- skill 后续应当如何持续优化与升级。

本文面向当前 `tingyun` 项目本身，围绕仓库已经形成的三段式链路展开：

1. 能力供给与数据抽取侧；
2. 远程消费、对象收束与素材生产侧；
3. 成文、归档与正式交付侧。

因此，这里讨论的 skill 不是抽象意义上的“大模型技能”，而是：

> 围绕当前项目中的诊断对象、证据链、判断逻辑与报告表达所建立的一套可复用工作单元。

## 2. 为什么这个项目需要 skill

当前项目的根本目标，不是为了“多抓一些接口”或“多沉淀一些文件”，而是为了围绕“对象 - 证据 - 判断 - 表达”形成一条稳定链路，最终向开发、运维和后续排障人员提供尽可能明确、可验证、可执行的结论。

这意味着项目中的关键价值并不只在于：

- 调到了哪些平台接口；
- 导出了哪些 CSV/XLS；
- 生成了哪些中间表格；
- 能不能把内容拼成一篇报告；

更在于：

- 我如何判断哪些对象值得关注；
- 我如何围绕这些对象继续深挖；
- 我如何把看到的现象转成可复核的证据链；
- 我如何把问题归并成研发真正能理解、能行动的表达。

如果这些能力只是停留在“这次对话里临时告诉 Codex 怎么做”，就会出现几个问题：

1. 每次都要重新讲一遍，成本高；
2. 不同批次、不同 agent、不同接手人之间行为不稳定；
3. 经验很难积累，只会散落在对话和临时笔记里；
4. 项目难以从“能跑一次”走向“可持续复用”。

因此，建立 skill 的意义在于：

> 把项目中已经逐步形成的“诊断套路、取数顺序、判断经验、表达规则”沉淀成一套稳定、可传递、可演进的工作单元。

## 3. skill 能否先用自然语言来描述

答案是：完全可以，而且非常适合当前阶段先这样做。

当前项目里的很多 skill，本质上并不是一个单独 API，也不是一个单独命令，而是一整套诊断思路。例如：

- 如何从 request 主表中筛出高价值对象；
- 如何结合 evidence index 判断某个对象是否值得 deep-dive；
- 如何判断一个慢接口更像数据库问题、应用层问题还是依赖问题；
- 如何把多个对象归并成问题簇后再进入报告；
- 如何在第三阶段直接围绕 diagnostics 生成报告，而不是再复制一份输入包。

这些东西如果一开始就被写成硬编码规则，往往会过早收窄，而且会把尚未稳定的经验误写成“铁律”。

所以当前仓库采用的策略是：

> 先用自然语言把 skill 的意图、输入、流程、判断和缺失处理讲清楚，再逐步补轻量契约，让它变成稳定可执行的 skill。

这也是为什么当前仓库根已经先落下了 `skills/` 目录，并采用每个 skill 一个目录、目录下一个 `SKILL.md` 的轻量形态。

## 4. 自然语言描述与可执行 skill 的转化方式

skill 的形成更适合被理解为三层递进结构。

### 4.1 意图层

这一层最适合完全使用自然语言。它回答：

- 这个 skill 是干什么的；
- 它服务于哪个阶段；
- 它为谁服务；
- 在什么场景下应该用；
- 在什么场景下不应该用。

例如：

> `request-diagnosis-skill` 用于围绕 `request_master.csv` 中的重点对象，形成可进入报告 2.2 章节的对象分析素材；它服务于接口问题的筛选、深挖和成文映射，不直接用于主机资源盘点。

### 4.2 流程层

这一层仍然以自然语言为主，但已经进入可执行说明。它回答：

- 先读什么；
- 再看什么；
- 看到什么信号时优先怀疑什么；
- 何时进入 deep-dive；
- 何时停止并占位；
- 最后输出什么。

### 4.3 契约层

这一层开始进入半结构化描述。它回答：

- skill 的输入文件是什么；
- 必填输出是什么；
- 缺失值规则是什么；
- 哪些结论禁止直接写；
- 成功与失败如何判断；
- 结果应该落到哪个目录、哪个文件中。

因此，所谓“自然语言与 skill 的转化”，不是从自然语言直接跳到代码，而是：

> 自然语言方法论 -> 流程化说明 -> 半结构化契约 -> 部分自动化。

## 5. 一个良好建设的 skill 应该包含哪些内容

当前仓库中的 `SKILL.md` 已经按较统一的结构落地。一个成熟的项目级 skill 至少应包含以下内容：

- Goal
  - 这个 skill 的核心目标是什么
- Scope
  - 在什么情况下使用，什么情况下不使用
- Inputs
  - 应优先读取哪些 diagnostics、主表、证据索引、deep-dive 或模板资产
- Outputs
  - 结果应形成什么类型的产物，例如对象清单、章节素材、截图计划、tex 骨架、report context
- Core Process
  - 明确先做什么、再做什么、何时切换到下一级、何时停止、何时输出
- Judgment Rules
  - 承载高置信判断经验，例如高请求量 + 高慢次数优先级更高
- Common Misjudgments
  - 用于抑制误判和过度归因
- Missing Policy
  - 明确哪些情况算证据不足，缺数据时输出什么、哪些内容禁止臆测
- Definition Of Done
  - 定义 skill 完成的最小可验收标准

## 6. 当前项目大致需要多少个 skill

如果目标是让整套系统比较稳定地运行，我建议把项目理解为需要 12 个核心 skill，再加 2 个扩展 skill 会更完整。

### 6.1 理想状态下的核心 skill 总表

| 编号 | Skill 名称 | 核心目标 | 所属阶段 | 当前重要性 |
|---|---|---|---|---|
| 1 | 平台能力发现与可用链路确认 skill | 确认可稳定使用的听云链路、抓取样本和 adapter 能力入口 | 能力供给侧 | 高 |
| 2 | 诊断批次初始化与原始导出归档 skill | 建立某次诊断 batch 的工作区和导出归档基础 | 阶段一前置 | 高 |
| 3 | 主表准备表生成 skill | 把原始导出转成 prepared/master 的稳定基础 | 阶段一 | 高 |
| 4 | 应用整体状态识别 skill | 识别整体状态、重点应用与全局异常背景 | 阶段一 | 中高 |
| 5 | 请求 / 事务候选池筛选 skill | 建立接口/事务对象的第一轮重点对象池 | 阶段一 | 最高 |
| 6 | 接口簇归并与服务接口摘要 skill | 把多个 request 提升到接口簇/服务接口视角 | 阶段一到二 | 中高 |
| 7 | SQL 候选池与 SQL 主表生成 skill | 建立慢 SQL / 高耗时 / 高错误 SQL 的对象池 | 阶段一 | 最高 |
| 8 | NoSQL / 组件操作补充识别 skill | 识别 NoSQL、缓存、组件操作对问题的补充意义 | 阶段一到二 | 中 |
| 9 | 对象深挖 skill | 围绕对象看 trace、依赖、瓶颈主体和问题簇线索 | 阶段二 | 最高 |
| 10 | 证据挂接与截图计划 skill | 沉淀 URL、trace 入口、截图位与回查路径 | 阶段二到三 | 高 |
| 11 | 问题簇归并与写作映射 skill | 把多个对象归并为可写作的问题簇和章节素材 | 阶段三前置 | 高 |
| 12 | 报告生成 skill | 按模板、spec、guidelines 生成正式报告 | 阶段三 | 最高 |

### 6.2 扩展 skill

| 编号 | Skill 名称 | 核心目标 | 所属阶段 |
|---|---|---|---|
| 13 | 缺失项与可信度控制 skill | 专门处理证据不足、不能下结论、必须占位的情况 | 阶段二到三 |
| 14 | 回归测试与产物复核 skill | 对不同批次、多次生成后的结构与产物稳定性做回归检查 | 阶段三后置 |

### 6.3 当前仓库已经落下的第一批 skill

当前仓库还没有一次性把 12 到 14 个 skill 全部铺开，而是先按“文档型核心 skill”落了第一批更关键的工作单元：

- `request-diagnosis-skill`
- `sql-diagnosis-skill`
- `report-generation-skill`
- `master-table-materialization-skill`

这表示仓库当前处于“先把主链路压实，再逐步向完整 skill map 扩展”的阶段，而不是从一开始就搭满全部 skill。

## 7. 经验判断是否应该进入 skill

答案是：应该，而且越早进入越好。

因为这个项目里最有价值的，并不只是“有哪些字段”，而是：

- 看到这些信号时应先怀疑什么；
- 哪些现象经常一起出现；
- 哪些对象适合放在一起讲；
- 哪些判断不能轻易下；
- 哪些 trace、SQL、页面入口最值得先看。

但经验判断不应原样塞进去，而应分层精炼。

### 7.1 高置信经验

最适合直接进入 skill 的 Judgment Rules，例如：

- 高请求量 + 高慢次数优先级高；
- SQL 时间占比高时优先怀疑 SQL / 装配问题；
- 错误率高但平均响应低时优先怀疑快速失败；
- 没有足够 evidence 时不要写确定性根因。

### 7.2 中置信经验

更适合写成“优先怀疑方向”或“进一步验证路径”，例如：

- 上传、预览、在线查看这类接口常常不是单点问题，而是同一问题簇的不同入口；
- 页面装配型接口的慢，可能来自多个分散 SQL 叠加；
- 某些高错误接口并不一定是性能问题，也可能是快速失败或调用口径问题。

### 7.3 低置信经验

暂时不适合直接写进正式 skill，应沉淀到：

- judgment log；
- review queue；
- notes；
- 待确认 heuristics。

## 8. 经验应如何精炼到 skill 中

当前更适合通过四种方式把经验沉到 skill：

### 8.1 精炼成“观察模式”

格式可固定为：

- 触发条件；
- 优先怀疑；
- 进一步验证；
- 不要误判。

### 8.2 精炼成“诊断 checklist”

把经验转成固定检查顺序，例如：

1. 先看主表排序字段；
2. 再看 evidence 状态；
3. 再看 deep-dive；
4. 再归并问题簇；
5. 再输出章节素材。

### 8.3 精炼成“判断规则”

把高置信经验抽成更稳定的规则，例如：

- 若 `error_rate` 高且 `avg_rt` 低，则优先检查快速失败；
- 若多个 request 共享同一 cluster hint，则优先归并讲述；
- 若 SQL 时间占比高，则优先进入 SQL 方向深挖。

### 8.4 精炼成“反例与禁忌”

用于抑制误判，例如：

- 不要因为看到了慢 SQL 就把所有问题都归因给 SQL；
- 不要因为请求量低就完全忽略极慢初始化对象；
- 没有证据时不要补造根因；
- 不要把 diagnostics 覆盖边界误认为是生成器 bug。

## 9. 除了 skill 本身，这些经验还应沉淀到哪里

我不建议把所有经验都只放在 skill 文档里。更合理的是分三处沉淀：

### 9.1 skill 文档

适合已经足够稳定、能直接指导执行的经验。当前仓库里的主入口就是：

- `skills/<skill-name>/SKILL.md`

### 9.2 judgment log / review queue / notes

适合那些还在生长、还未验证充分的经验。

结合当前仓库现状，这一层还没有形成统一的 repo 级 judgment log 目录。现阶段更现实的承载位置是：

- `knowledge/monitored_systems/<system_key>/`
  - 系统级长期上下文与 review queue
- 各批次 `artifacts/.../<batch_key>/diagnostics/04_deep_dive/.../notes.md`
  - 对象级深挖备注
- 某些临时演进判断先放在模板 `notes.md`、实例 README 或相关工作流文档中

这意味着：项目已经有经验沉淀位置，但统一经验库仍有继续补齐空间。

### 9.3 chapter guidelines

适合那些与最终报告表达方式强相关的经验。例如：

- 哪些对象应优先归并；
- 哪些内容先表格后分析；
- 哪些章节缺信息时必须占位；
- 哪些内容不应写成确定性建议。

当前这类经验已经部分落在：

- `report_templates/legal_diagnostic_report/chapter_guidelines.md`
- `docs/reporting/`

因此，经验最合理的沉淀方式不是“全都塞进 skill”，而是：

> skill 执行经验，notes / review queue 积累待验证经验，chapter guidelines 固定表达经验。

## 10. skill 的优化与提升路径

我建议把 skill 的成长过程理解为 5 个阶段。

### 阶段 1：经验笔记

先把脑子里的经验写下来，避免经验继续散落：

- 常见现象；
- 常见判断；
- 常见误判；
- 常见缺失处理。

### 阶段 2：自然语言 skill

把经验整理成“目标 + 场景 + 流程 + 判断 + 缺失处理”的文档。当前仓库的 `SKILL.md` 主要处于这一层和下一层之间。

### 阶段 3：checklist 化 / 半结构化

把自然语言方法论进一步压成：

- 输入；
- 输出；
- 步骤；
- 规则；
- 占位策略；
- 验收标准。

当前仓库中的四个核心 skill，已经明显进入这一层。

### 阶段 4：规则抽取

把高置信经验从自然语言里抽成更稳定的规则、配置或逻辑，例如：

- 排序权重；
- 优先级规则；
- 归并规则；
- 占位规则；
- 结构生成约束。

这一层在当前项目中已经部分落到：

- `tingyun_adapter_client` 的主表物化逻辑；
- deep-dive registry / bundle materialization；
- 第三阶段 report renderer；
- `spec.yaml` 与 chapter guidelines。

### 阶段 5：部分自动化

把最稳定的部分交给代码或脚本完成，例如：

- 自动筛选候选对象；
- 自动生成 missing items；
- 自动建立章节骨架；
- 自动检测 evidence 是否足够；
- 自动拼接 tex 与编译 PDF。

当前第三阶段已经开始具备最小 renderer 骨架，因此 skill 的演进并不是停留在文档层，而是已经开始进入“文档型 + 半自动化”的状态。

## 11. 一个 skill 变好的标志是什么

一个 skill 的成熟，不在于它写得多长，而在于它是否出现了以下变化：

1. 从“我觉得”变成“我通常这样判断”；
2. 从“随手分析”变成“固定检查顺序”；
3. 从“同样输入输出差异很大”变成“同样输入输出较稳定”；
4. 从“经验只在我脑子里”变成“别人也能照着做”；
5. 从“只能解释”变成“能驱动脚本、配置或生成器”。

这几个变化，实际上就是 skill 从“方法”走向“工程资产”的标志。

## 12. 当前仓库的第一轮建设顺序与后续建议

如果从当前仓库现状往回看，这一轮更合理的建设顺序已经逐步清晰了：

1. 先把最关键的主链路 skill 落成文档型 skill；
2. 再把高置信规则继续沉到主表流水线、deep-dive 和第三阶段生成器；
3. 再补统一经验库、judgment log 和更多细分 skill。

当前第一轮已经落下的重点是：

- request 诊断；
- SQL 诊断；
- 主表物化；
- 报告生成。

接下来更值得补的方向是：

- 接口簇归并与问题簇映射；
- 证据挂接与截图计划；
- 缺失项与可信度控制；
- 回归测试与产物复核；
- 一个统一的 APM 诊断 heuristics / references 入口。
