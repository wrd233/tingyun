# 最终交付物形态与报告表达说明（整理稿）

> 本文档是当前最终交付物形态与报告表达方式的主设计文档。

## 1. 文档定位

这份文档聚焦于最终交付物的形态，以及我希望如何把前面分析阶段得到的对象、证据和判断，组织成正式可交付的表达。这里讨论的重点不是具体排版技巧，而是最终需要交付什么、这些交付物之间如何配合、报告中应该写什么，以及前面的工作流为什么必须围绕这些交付要求来设计。

本文尽量复用我原本的语言，只做结构化整理与少量补充，并统一改成我的视角。

## 2. 我理解中的最终交付物，不只是一份报告正文

我目前设想中的最终交付物，并不只有一份报告正文，而是一个由“正式表达 + 辅助材料”共同组成的输出集合。

其中，正式表达主要是一份调研/巡检报告；辅助材料则可能包括 Excel、CSV、JSON 或其他便于二次处理与复核的中间文件。之所以强调这一点，是因为报告中的很多判断并不是凭空得出的，它需要被若干可检索、可排序、可核验的材料支撑。

因此，最终交付不应该只是“交一篇文章”，而应该是一套彼此对应的交付件：

- 正式报告正文；
- 对象清单与排序结果；
- 证据索引与回查入口；
- 必要的中间表格或附属材料；
- 便于复核和二次加工的结构化文件。

## 3. 最终被接受、也最值得沉淀的内容

从我现在的理解来看，最终报告中最值得被接受、也最应该稳定沉淀下来的内容，大致包括以下几块。

### 3.1 检测范围与对象边界

报告需要先说明本次巡检的系统是什么，时间范围到哪里为止，哪些资产、应用、接口、数据库或其他对象被纳入观察，哪些没有被纳入。

这里既包括资产清单，也包括这些资产之间较为简洁的关系说明。这样做的目的，是先把“我到底看了什么、没看什么”交代清楚，避免后续判断失去边界。

### 3.2 系统整体状态

报告需要说明系统在整体层面的运行情况，包括总体指标、整体趋势、面板化信息、图表化说明等，用来回答两个基础问题：

- 系统是不是整体有问题；
- 问题更像是局部的，还是全局性的。

这一部分不只是为了“显得完整”，而是为了给后面的重点对象分析提供全局背景。

### 3.3 重点接口、SQL 与其他关键对象

这是报告中最重要的一部分。这里不仅要列出重点对象，还要说明：

- 我为什么关注它们；
- 它们的排序依据是什么；
- 这些对象之间是否存在关联；
- 它们各自的成因或根因是什么；
- 哪些建议是我有把握写入报告的。

归根结底，报告真正要交付的，不是“接口列表”，而是“重点对象及其证据链”。

## 4. 我为什么强调“重要对象清单”这一类中间产物必须进入最终交付体系

在我当前的设想中，当我对系统本身还不够了解时，最容易让人信服、也最直接的方式，就是先把重要对象拉出来，给出它们的清单，并按若干启发性原则进行排序。

这些启发性原则可以包括：

- 平均响应时间；
- 错误率；
- 调用次数；
- 总体耗时；
- 慢调用次数；
- 其他能够反映风险、影响面或异常密度的指标。

这种方式的价值在于：

1. 它不依赖我一开始就对业务有很深的背景知识。
2. 它可以快速形成一个“从哪里看起”的入口。
3. 它天然适合作为中间表格和最终报告表格的共同基础。
4. 它有助于把“对象的重要性”从模糊判断，转成可解释、可排序、可复核的形式。

因此，在最终交付体系里，一个非常重要的组成部分，应该是：**按一定启发性原则排序的重要对象清单，以及这些对象的关键运行参数。**

## 5. 报告中的表达方式设想

我希望报告不是一上来就写长篇分析，而是先通过表格把重点对象列出来，把它们的关键运行参数放上去，并在表格中直观标出异常处，例如：

- 响应时间过高；
- 错误率过高；
- 调用次数较大；
- 慢调用次数突出。

在此基础上，再在表格下方对其中重点对象进行分析。这个分析既可以覆盖全量，也可以只覆盖重点，但无论哪种方式，都不应再是零散描述，而应尽量把存在潜在联系的问题放在一起讲清楚。

这种写法尤其适合接口与 SQL 这两类问题：

- 先表格化罗列对象与指标；
- 再围绕重点对象展开根因、成因与证据分析；
- 必要时把几个相关对象归并到一个问题簇中统一叙述。

因此，我希望报告中的“问题分析部分”本质上是一种 **对象清单 + 重点归并分析** 的结构，而不是“排行榜 + 零散点评”。

## 6. 对最终交付物中“证据”的要求

后续写报告不仅需要结论和表格，还需要可回查的证据。这里有两个关键点。

### 6.1 证据必须可反向核验

落盘的证据不能只是模型的一段描述，而必须让我在之后能够反向验查，知道它来自哪里、如何再次打开、对应的是哪一个对象、哪一条 trace、哪一个依赖或哪一个页面入口。

因此，证据本身至少应满足：

- 能定位到具体对象；
- 能说明其与当前问题之间的关系；
- 能被后续人工复核；
- 能支撑正式报告中的论断，而不仅仅是作为“看过了”的痕迹。

### 6.2 图片未必由系统直接生成，但至少要有截图位与取证路径

当前阶段我不一定能够直接从听云网页端自动截图，因此这件事很可能需要人工完成。但即便如此，也不能因此让“图片证据”完全脱离流程。

更合理的做法是：

- 在分析过程中保留能够打开对应对象页面的 URL；
- 在需要写报告的位置预留图片占位；
- 在占位旁说明“应从哪个 URL 打开什么页面、截取什么内容、用来说明什么问题”。

这样一来，即使图片不是自动生成的，证据链也仍然是完整的。

> 待确认：是否要把截图占位标准化，例如统一成“截图目的 / 页面 URL / 建议截图区域 / 说明对象 / 用途说明”这类固定模板。

## 7. 报告写作路径的思考

我当前考虑保留两条写作路径：

1. 将素材输入给 ChatGPT，直接整合成 Word 文档。
2. 继续使用 Codex 等 agent，把素材汇总成 LaTeX 格式报告，再尝试导出为 Word 或 PDF。

这里真正的问题不只是“Word 还是 LaTeX”，而是：

1. 报告成文过程要尽量减少风格漂移；
2. 模板要尽量掌控格式与章节组织；
3. 中间素材到正文的转换要尽量可追溯；
4. 最终交付如果仍要求 Word，那么 LaTeX 只能在不破坏这一要求的前提下发挥作用。

基于我目前的判断，LaTeX 更适合作为一个中间过渡层，用来稳定格式、降低文字漂移；最终我还是需要 Word 或 PDF，而且优先选择 Word。

## 8. 前面的工作流为什么必须围绕最终交付形态来设计

我之所以这么强调最终交付物的形态，是因为报告中要写什么、怎么写、哪些内容能被接受，本身就决定了前面应该怎样取数、怎样组织中间产物。

例如：

- 报告需要写检测范围和对象边界，那么前面就必须保留足够清晰的资产与范围信息。
- 报告需要用表格说明重点接口和 SQL，那么前面就必须生成可排序、可复用的对象主表。
- 报告需要体现证据链，那么前面就必须沉淀可反向核验的 URL、trace 入口和截图提示。
- 报告需要减少 AI 味、增强可执行性，那么前面就要尽量把对象、证据、归因线索组织好，而不是把大量半成品问题留给写作阶段。

因此，整个项目不是“前面分析、后面写作”这么简单，而是“后面的表达要求反过来塑造前面的能力形态”。

## 8.1 主表、证据索引和 report bundle 的关系

围绕 diagnostics 目录，我现在更明确地把主线理解为：

- `00_raw_exports/`
- `01_prepared_tables/`
- `02_master_tables/`
- `03_evidence_indexes/`

其中：

- 准备表仍然保留全量，并由代码完成归一、多文件整合和首轮筛选注记；
- 主表才是人工持续更新、写报告和复核时真正依赖的工作底稿；
- 证据索引和写作输入应由主表再派生；
- report bundle 仍然是最终交付体系的一部分，但不应反向替代主表成为主线对象。

## 9. 当前仓库中已经出现的交付物雏形

从当前仓库已经呈现出来的方向看，我的最终交付体系其实已经有了一些雏形。样例报告包 `samples/monitored_systems/bizsystem_1065/2026-04-monthly-diagnostic-sample/report_bundle/` 中已经出现了如下类型的文件：

- `01_exec_summary.md`
- `02_writer_input.md`
- `03_issue_matrix.csv`
- `04_evidence_index.csv`
- `05_review_bundle.json`

这些文件说明我现在并不是从零开始思考“最终要交付什么”，而是已经开始形成如下几类东西：

- 面向阅读者的摘要性表达；
- 面向写作者的输入材料；
- 面向问题筛选和排序的矩阵；
- 面向证据回查的索引；
- 面向复核与归档的结构化包。

这个方向与我当前对最终交付物的理解是一致的，后续需要做的，是把这些产物继续补齐、稳定、统一，而不是推倒重来。

## 10. 我真正想得到的最终效果

我最终希望交付出来的，不是一份“写得像报告”的报告，而是一套真正能被使用的东西：

- 对负责人来说，可以快速把握风险与优先级；
- 对研发和运维来说，可以直接拿去定位与整改；
- 对后续的架构分析、性能治理和复盘来说，可以形成后续行动项；
- 对我自己来说，可以回查、复核、再加工，而不是写完即散。

因此，最终交付物的价值，不在于它形式上有多完整，而在于它是否真的把“对象—证据—判断—表达”这一条链路落到了文件上，并且让后续的人能够沿着这条链路继续往下走。

## 11. 这份文档的作用

这份文档的作用，是先把我对最终交付物形态和报告表达方式的要求压实下来。后续无论我是继续优化 adapter 的导出、整理对象主表、设计证据索引，还是选择 ChatGPT / LaTeX / Word 的成文路径，都应该回到这里检查：

- 最终到底要交什么；
- 这些交付件之间是否彼此支撑；
- 报告中的表格、分析、证据和辅助材料是否形成了闭环；
- 交付出来的东西是否真的能帮助开发人员理解系统发生了什么、为什么重要、根因可能是什么、优先该看什么。
