## 1. 这份文档要回答什么

这份文档主要回答 4 个问题：

1. 这次基于 adapter + client + live pack 生成月度巡检报告，积累了哪些有效经验。
2. 如果要达到参考 Word 报告那种“覆盖面比较全”的程度，我们还缺什么能力。
3. 如果目标不是“像参考报告”，而是做出一份真正面向工程师、能指导调优的完整报告，我们还缺什么能力。
4. 后续应该用什么思路来建设 adapter / skill / report pipeline，避免把报告做成“接口结果堆叠”或“低频异常排行榜”。

## 2. 这次报告建设中已经建立起来的经验

### 2.1 最重要的经验：报告不应从页面出发，而应从诊断骨架出发

这次最关键的进展，不是“又多抓到了一批接口”，而是我们已经不再把这些 API 看成页面抓包碎片，而是开始按诊断骨架来组织：

- 业务系统
- 应用 / 实例
- action / 事务
- trace
- 下游组件：Database / NoSQL / 连接池

这个转变非常重要，因为它决定了后续报告不是“按页面截图写说明”，而是按对象、关系、证据和下钻路径来写。

### 2.2 adapter 的价值已经被证明

这次月报能顺利产出，说明 adapter 这层设计方向是对的。它已经显著降低了模型理解听云原始接口的成本，主要体现在：

- 把跨接口键关系整理出来了。
- 把 `action -> trace -> detail` 这种链路封装成了 pack。
- 把 `evidence`、`suspect_signals`、`drilldown_keys` 这些对报告和分析非常有用的信息稳定化了。
- 屏蔽了原始接口字段不统一的问题，比如：
  - `response / respTime / responseTime`
  - `throught`
  - 数值型 `traceId` 与 GUID 型 `traceGuid / actionGuid`

如果没有 adapter，这次报告很难做到“既有整体判断，也有链路证据，也能继续下钻”。

### 2.3 报告生成已经证明“候选筛选 + 深挖”是有效路径

这次最成功的工作流不是直接从 `system_snapshot` 写到报告，而是：

1. 先拿总体快照。
2. 再拿 `diagnostic_candidate_pack`。
3. 对重点 action 拉 `action_fact_sheet`。
4. 对典型 trace 拉 `trace_fact_sheet`。
5. 再把月度总体、热点对象、典型问题链路组织成开发报告。

这个顺序是有效的，因为：

- 先有全局视角。
- 再收敛重点对象。
- 最后有可供开发定位的证据。

这比“直接把 top N action 摆出来”强很多。

### 2.4 面向工程师的报告，必须包含“判断”

这次报告之所以比普通指标摘要更像“分析报告”，核心在于已经引入了技术判断，例如：

- 平均值正常，不代表系统没有问题，真正的问题是“尾部失真”。
- 某些分钟级事务可能不是高频用户主链路，而是初始化/统计型调用。
- `upload` 这类调用虽然次数少，但因为真实报错且面向用户，优先级更高。

也就是说，报告不能只说：

- 响应时间是多少
- 错误率是多少
- 哪个接口最慢

还必须说：

- 这件事为什么重要
- 它更像什么问题
- 为什么它应该排在前面

### 2.5 低频极慢不一定重要，这个原则必须上升为方法论

你提到的这一点非常关键：

> 长时间内仅仅调用了很少次数的可能没那么重要。

这次月报里其实已经出现了这个问题：

- `afterPropertiesSet`
- `lawyerEorkTimeTop10Data.dwr`

这些事务极端慢，但低频，而且其中一部分可能存在命名异常或初始化逻辑混入的情况。它们确实值得关注，但不能天然排在真实失败的用户请求前面。

所以，后续报告系统不能继续采用“按响应时间从高到低排序 = 重要性排序”的思路，而要引入更完整的“影响度评估”。

## 3. 参考 Word 报告带来的启发

参考报告的优点主要有三个：

### 3.1 覆盖面广

参考报告不是只看 Java 应用本身，而是同时覆盖：

- 应用健康度
- 拓扑
- Apdex
- 访问趋势
- 实例
- 外部接口
- 错误
- 慢接口
- 错误接口
- 数据库整体
- 慢 SQL / 异常 SQL
- 页面性能
- 慢页面
- 慢请求
- JS 错误
- 地域
- 浏览器

这说明，如果目标是“完整巡检报告”，仅靠当前后端/APM 主链路还不够。

### 3.2 它已经有“问题清单”和“建议清单”

参考报告不是停留在检查结果，而是进一步形成了：

- 问题编号
- 问题描述
- 处理建议
- 优先级
- 责任人 / 日期占位

这对落地执行非常重要。

### 3.3 它已经体现了“行业建议值”和阈值意识

例如：

- 接口响应时间超过 `1s`
- 错误率超过 `1%`
- 页面首屏时间建议值 `3s`
- 完全加载建议值 `5s`

这说明一个成熟的巡检报告，不仅描述现状，还要把现状映射到某种可解释标准。

## 4. 但参考报告也有明显局限

虽然参考报告覆盖面广，但它也比较简陋，主要体现在：

### 4.1 更像“巡检 checklist”，不像“工程分析报告”

它大量采用：

- 存在哪些慢接口
- 存在哪些高错误接口
- 存在哪些慢 SQL

这种句式。

但它没有很好回答：

- 为什么这些问题值得优先处理
- 哪个问题对用户影响最大
- 哪个问题最可能是代码问题，哪个更像环境问题
- 哪些问题本质上是同一条链路的不同表现

### 4.2 根因分析比较浅

例如它会说：

- 某接口慢，是因为慢 SQL
- 某接口错误，是因为代码异常
- 某接口慢，是因为某个 Filter 慢

这已经不错，但还不够像开发真正需要的报告。开发更希望看到：

- 慢 SQL 是哪一类 SQL
- 是大表扫描还是索引失配
- Filter 慢是等待远程接口、Redis、认证还是线程池
- 这条链路在请求生命周期里占比多少

### 4.3 缺少“影响度排序”的方法

参考报告仍然比较接近“超过阈值就列出来”，但没有很好区分：

- 高频中度慢
- 低频极端慢
- 高频高错误
- 低频失败但面向关键用户

这会导致问题清单很长，但开发团队不容易知道“先做什么最值”。

## 5. 如果要达到参考报告那种“覆盖程度”，我们还缺什么能力

如果目标只是达到“覆盖面广”的程度，而不要求特别深入，当前还缺下面这些能力域。

### 5.1 更完整的应用域覆盖

当前我们已经有：

- 系统总览
- action 热点
- trace
- Database / NoSQL / 连接池

但还缺：

- 外部 HTTP 接口访问分析
- 应用实例专项分析
- 错误码 / 异常类型分布
- 拓扑视角的上游 / 下游关系汇总

### 5.2 SQL 细粒度能力还不够

虽然我们已经具备数据库组件视角，但距离“慢 SQL / 异常 SQL 专章”还差不少：

- 需要能稳定拿到 SQL 级对象，而不仅是数据库组件级对象。
- 需要把 SQL 与 action / trace 建立映射。
- 需要能做：
  - 慢 SQL TopN
  - 异常 SQL TopN
  - SQL 类型统计
  - SQL 所属接口 / 事务映射

### 5.3 前端 / 页面用户体验能力还没接入

参考报告里有专门的页面体验章节，而我们当前基本仍是后端/APM 视角。还缺：

- 页面性能 pack
- 慢页面 pack
- JS 错误 pack
- 浏览器分布和性能 pack
- 地域访问 pack

### 5.4 外部服务与三方依赖分析不足

参考报告里已经把第三方接口慢、错误率高的地址列出来了。我们当前还缺：

- 外部 HTTP 依赖 pack
- 第三方服务错误率和响应时间 pack
- 外部调用与内部 action / trace 的映射

### 5.5 标准阈值体系还不完整

参考报告虽然简单，但它至少有阈值。

我们当前还缺一套可配置的巡检标准库，例如：

- 后端接口建议响应时间
- 错误率阈值
- 页面首屏阈值
- JS 错误率阈值
- SQL 慢阈值

没有这套标准，报告就容易变成“事实列表”，而不是“达标/不达标 + 风险说明”。

## 6. 如果要做一份真正面向工程师、完整的报告，我们还缺什么能力

如果目标更高，不只是覆盖面广，而是要做出“开发看到就能直接开始排查和优化”的报告，那我们还缺的能力会更多，而且重点不只是“多几个接口”，而是“更强的分析组织能力”。

### 6.1 缺“影响度模型”

这是当前最关键的缺口。

我们需要的不是简单 TopN，而是一个综合排序模型，用来区分：

- 高频中慢
- 低频超慢
- 高频高错误
- 低频但强业务关键路径失败
- 低频初始化型调用

建议后续引入一套 `impact score` 思路，至少考虑这些维度：

- 调用次数
- 慢请求数
- 错误数 / 错误率
- 总耗时
- 平均耗时
- 是否是用户入口
- 是否影响关键业务链路
- 是否在多个实例 / 应用复现
- 是否可被 trace 证据支撑

一个很实用的原则是：

- **用户失败 > 高频慢 > 高频错误 > 低频极慢但无业务影响**

### 6.2 缺“业务关键性”建模

并不是所有 action 都同等重要。

例如：

- 登录
- 上传
- 待办
- 审批
- 列表页
- 报表页
- 预热 / 初始化

对业务的影响完全不同。

所以更完整的工程报告，应该允许引入：

- 业务关键路径标签
- 用户入口标签
- 后台任务标签
- 初始化 / 统计型标签

这类标签可以来自：

- 规则
- 命名模式
- 人工配置
- 未来的 skill 判断

### 6.3 缺“重复性与稳定性”判断

一次慢、两次慢、每天都慢，性质完全不同。

所以后续报告应该能回答：

- 这是偶发还是持续
- 集中发生在哪几天 / 哪几个时段
- 是单实例问题还是全应用问题
- 是单链路异常还是系统性问题

也就是说，我们还需要更强的时间分布和稳定性分析。

### 6.4 缺“关联能力”

开发更希望看到的是问题链，而不是分散现象。

例如：

- 慢接口
- 对应慢 SQL
- 对应数据库实例
- 对应典型 trace
- 对应代码热点

如果这些能串起来，开发会更容易行动。

当前我们已经有一部分链路，但仍然不够完整，特别是：

- action ↔ SQL
- 页面 ↔ action
- 外部接口 ↔ action
- 异常类型 ↔ 具体代码位置

### 6.5 缺“变化感知”

一份真正好的月报，不应该只说“现在有哪些问题”，还应该说：

- 比上个月变好了还是变差了
- 哪些问题是新出现的
- 哪些问题已经消失
- 哪些问题在扩大

这意味着我们后续还需要：

- 历史 pack 存档
- 同口径对比能力
- 变化检测能力

### 6.6 缺“建议生成的工程化模板”

现在我们已经能写出建议，但还比较依赖人工组织。

更成熟的体系应该把建议分层：

- 快速止血建议
- 结构性优化建议
- 监控补强建议
- 验证回归建议

并且建议需要和问题类型绑定，例如：

- `Filter / Listener` 慢：建议看前置逻辑和远程依赖
- `Database` 访问次数高：建议查 N+1 和 SQL 聚合
- `NoSQL` 操作密度高：建议查循环调用与缓存命中策略
- `HTTP 500`：建议先拿根异常和调用上下文

## 7. 报告排序不能只看“谁最慢”

你特别指出的这个问题，应该成为后续报告系统的核心设计原则。

### 7.1 为什么“谁最慢”不够

如果只按平均响应时间排序，就会出现这些问题：

- 一条 30 天只调用 1 次、耗时 30 分钟的初始化事务排在第一
- 一条每天都失败、每次 20 秒的上传请求排在后面
- 一条低频报表接口被排在关键交易接口前面

这会误导开发团队。

### 7.2 更合理的思路：分层优先级

建议把问题分成至少 4 层：

#### 第一层：用户失败类

例如：

- HTTP 500
- 高错误率
- 关键用户入口失败

优先级最高。

#### 第二层：高影响性能类

例如：

- 高频且慢
- 总耗时高
- 多实例复现

#### 第三层：结构性风险类

例如：

- 下游组件访问密度极高
- 明显 N+1
- 报表 / 统计型接口过重
- 连接池、外部接口波动

#### 第四层：观察项

例如：

- 极低频异常
- 一次性慢请求
- 命名可疑但暂未证实的初始化型事务

### 7.3 可落地的评分思路

建议在 adapter 或 skill 层引入 `priority_score`，但不是“最终判断”，而是“排序辅助”。可以考虑如下结构：

`priority_score = 业务影响 * 复现程度 * 失败程度 * 资源消耗 * 证据强度`

各维度可参考：

- 业务影响
  - 是否用户入口
  - 是否核心路径
- 复现程度
  - 调用次数
  - 慢请求数
  - 跨实例复现
- 失败程度
  - 错误率
  - 是否 HTTP 500
- 资源消耗
  - 总耗时
  - 下游调用密度
- 证据强度
  - 是否有 trace
  - 是否有 callTree
  - 是否有 SQL / 组件证据

这样才能避免“低频极慢”自动霸榜。

## 8. 后续能力建设思路

### 8.1 adapter 层

adapter 下一步应重点增加：

- 已于 2026-04-06 补齐：
  - `instance_analysis_pack`
  - `topology_dependency_pack`
  - `external_dependency_pack`
  - `slow_sql_pack`
  - `sql_fact_sheet`
  - `action_dependency_breakdown_pack`
- 当前暂缓：
  - `impact_signals`
  - `business_labels`
  - `stability_signals`
  - `comparison_signals`
  - `page_experience_pack`

adapter 不负责最终结论，但应该负责把这些“排序和判断所需的事实”整理出来。

### 8.2 skill 层

skill 不应该只做“把 pack 拼成一篇文章”，而应做：

- 优先级收敛
- 问题归并
- 问题链路组织
- 面向开发的解释和建议
- 月度总结与变化趋势描述

也就是说：

- adapter 负责事实和候选
- skill 负责解释和成文

### 8.3 report pipeline

后续建议形成稳定的报表流水线：

1. 拉取月度 pack  
2. 生成候选对象池  
3. 对关键对象自动补 fact sheet  
4. 计算优先级与问题分组  
5. 生成：
   - 摘要
   - 系统检查
   - 问题清单
   - 优化建议
   - 附录与证据  

## 9. 一份更完整的工程师报告应该长什么样

建议未来的完整版报告至少有这些章节：

1. 概述  
   - 报告对象、时间窗、数据来源、方法

2. 系统总体情况  
   - 健康、趋势、Apdex、实例分布

3. 本期核心发现  
   - 3~5 条最重要判断

4. 重点问题链路  
   - 每条问题用“现象 -> 影响 -> 证据 -> 判断 -> 建议”描述

5. 热点事务分析  
   - 不只是列表，还要分类

6. SQL / Database / NoSQL / 外部依赖分析  
   - 与 action / trace 关联

7. 页面与用户体验分析  
   - 如果接入前端能力

8. 问题清单  
   - 优先级、责任域、建议动作

9. 优化建议  
   - 分为短期、中期、长期

10. 附录  
   - 关键 trace、关键 SQL、关键 pack 引用

## 10. 当前阶段最值得优先补的能力

如果要按收益排序，我建议后续优先补下面 5 项：

1. 影响度排序模型  
2. SQL 级 fact sheet 与 action / trace 关联  
3. 外部依赖与错误类型 pack  
4. 历史对比与趋势变化能力  
5. 页面 / 用户体验侧 pack

## 11. 总结

这次月报建设说明我们已经跨过了最难的一步：

- 已经证明 adapter + pack + 深挖链路这条路线是可行的
- 已经能生成比普通“指标罗列”更像工程报告的内容
- 已经能让模型围绕对象、关系、证据和问题链路组织报告

但如果目标是做成一个真正成熟的、长期可用的工程巡检体系，后面仍然需要继续建设：

- 更广的能力覆盖
- 更强的影响排序
- 更稳定的历史对比
- 更完整的工程建议模板

最重要的是，后续一定要坚持下面这个原则：

**报告的目标不是把最慢的东西排出来，而是把最值得开发团队优先处理的问题排出来。**
