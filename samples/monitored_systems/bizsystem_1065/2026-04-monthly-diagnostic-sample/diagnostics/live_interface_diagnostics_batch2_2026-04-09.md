# Live 接口诊断（第二批）

数据来源：本地 `tingyun_adapter_client` 调用远端 adapter 的 `live` 数据。  
查询窗口：`bizSystemId=1065`，`endTime=2026-04-01 00:00`，`periodMinutes=146880`。

## SpringController/${url.rest.prefix.flowmobileapi.v1}/task-form-process/todo-pages/{id}

**[现状]**  
这个入口当前最需要优先处理的是高比例快速失败，而不是慢查询。live 指标显示两侧实例合并后请求约 7.15 万、错误约 1.35 万、错误率接近 19%。代表性错误样本在 10ms 内结束，状态直接是 `404`，异常里明确出现 `HTTP ERROR CODE: 404` 和 `NotFoundResourceException`。调用链主要停留在移动端过滤器和鉴权链路，数据库访问很轻，SQL 只有一次简单查询且耗时不到 1ms。现有证据说明，这个入口的主问题是请求在进入核心业务处理前就失败了。

**[建议]**  
先把 `404` 错误簇单独处理，不要和性能问题混在一起看。优先核对这个入口的路由命中、资源存在性校验、鉴权后资源可见性，以及参数对应对象是否存在。慢样本虽然也存在，但当前最直接影响成功率的是快速失败，建议先止血。

## SpringController/${url.rest.prefix.flowmobileapi.v1}/task-form-process/done-pages/{instId}

**[现状]**  
这个入口的核心问题比较集中，主因就是数据库重装配。live 指标显示两侧实例合并后请求约 1.38 万、平均耗时约 1.63s、错误约 1563、慢次数约 2734。代表性慢样本接近 8.6s，调用树里数据库节点超过两千，`executeQuery` 调用两千六百多次，数据库独占时间超过 7.6s。最重的一条 SQL 落在 `HD_FORM_OPINION`，单条就超过 6s，同时还伴随大量重复的 `HD_WF_HIS_USER`、`HD_WF_HIS_OPER`、`HD_WF_HIS_PRE` 查询。异常里虽然能看到 `ClientAbortException`，但发生在响应写出阶段，更像慢请求下的伴生结果，不是主瓶颈。

**[建议]**  
直接按“已办详情装配查库过重”来处理。优先检查意见、历史步骤、操作人、前驱步骤相关查询在一次请求中的执行次数，先确认是不是存在循环查库、逐条补数、重复读取，再考虑单条 SQL 优化。这里最需要先解决的是查询模式问题，不是外围异常。

## SpringController/serverapi/v1/flow-mobile/task-form-process/download-attachments-kfv/{code}

**[现状]**  
这个入口请求量和错误量都不低，live 指标显示合并后请求约 1.58 万、错误约 1248、错误率接近 8%。代表性样本本身不是失败请求，但能看出主耗时集中在 `AttachmentPreConversionController.downLoadAttachementKfv`，总耗时约 472ms，其中数据库只有一次轻量查询，耗时不到 1ms。现有证据更支持应用侧附件获取/预处理链路是主要耗时点，而不是数据库。

**[建议]**  
优先检查附件下载前的预处理、预转换、文件读取与返回链路，不要先从数据库入手。由于当前抓到的代表样本是成功请求，失败分支的直接证据还不够，建议继续对错误样本补 trace，重点确认文件存在性、鉴权校验和附件预处理失败分支。

## URI/grcv5/rest/mobile/thirdpartylogin.json

**[现状]**  
这个入口当前是稳定的高错误接口。live 指标显示合并后请求约 4.97 万、错误约 2682、错误率约 5.4%。代表性样本耗时约 369ms，主耗时不在过滤器，而是数据库查询，`executeQuery` 独占约 321ms；同时存在 HTTPS 外部调用，但耗时约 32ms，明显不是这一条样本里的主导部分。当前 trace 里最重的 SQL 是按 `APPID` 查 `HD_USER_YZJ` 的账号映射。

**[建议]**  
先检查第三方登录入口里的账号映射查询，不要先把重点放在外部接口。优先确认 `HD_USER_YZJ` 相关查询的执行方式、索引和调用频率，再结合错误样本看是否存在参数不合法或映射缺失。外部 HTTPS 调用仍然需要核对，但从当前 live 样本看，它不是首要瓶颈。

## URI/grcv5/wp/contractView/viewContract.htm

**[现状]**  
这个入口是典型的高流量页面装配偏慢问题。live 指标显示合并后请求约 11.38 万、平均耗时约 1.34s、错误约 1018。代表性样本耗时约 1.22s，其中数据库查询 148 次，累计时间约 1.04s，占了主要部分。SQL 分布也很分散，不是单条 SQL 异常，而是合同查看过程中存在多张合同扩展表、分组成员表、归档表、签署项表等多类查询叠加，页面装配型特征非常明显。

**[建议]**  
按“合同查看页装配查库过多”处理，不要先找单条超慢 SQL。优先梳理页面渲染前必须的数据集合，确认是否存在重复读取、多表逐段拼装和可合并查询的情况，再决定哪些 SQL 需要单独优化。这里的核心是减少一次请求里的查询扇出。

## SpringController/${url.workflow.edit}

**[现状]**  
这个入口流量很大，live 指标显示合并后请求约 16.18 万、平均耗时约 595ms、错误约 1137。当前抓到的代表样本本身并不慢，请求耗时约 155ms，调用树里能看到较频繁的数据库和 Redis 访问，但数据库累计时间只有约 47ms，没有出现单条特别重的 SQL。现有证据更像高频页面入口上的常规装配成本累积，而不是已经定位到某个明确的慢点。

**[建议]**  
先按高频页面装配入口来处理，重点检查编辑页初始化时的重复查询和不必要的数据读取。当前代表样本没有暴露出明确的主瓶颈，证据还不足以把问题压到某条 SQL 或某个方法上，建议继续补更慢的样本再判断是否存在稳定热点。

## SpringController/serverapi/v1/thirdParty/getOppDocking

**[现状]**  
这个入口的主问题比较明确，主要耗时集中在外部 HTTP 调用。live 指标显示合并后请求约 8.82 万、错误约 443。代表性样本耗时约 235ms，其中 `HttpRequestExecutor.execute` 占了约 186ms；数据库只做了很轻的插入和主键更新，累计时间约 1.5ms，可以排除数据库是主因。当前证据说明，这个接口的核心成本在对外依赖调用本身。

**[建议]**  
优先检查对外 HTTP 请求的超时、返回码处理、重试策略和参数校验，不要把精力放在数据库。尤其要确认外部返回异常时本地是否存在放大重试或日志型错误堆积，这个入口更适合按外部依赖链路排查。

## SpringController/${url.workflow.view}

**[现状]**  
这个入口和 `workflow.edit` 很接近，问题更像高频页面入口的装配成本累计。live 指标显示合并后请求约 5.74 万、平均耗时约 662ms、错误约 453。当前代表样本耗时约 117ms，数据库查询 76 次、累计约 36ms，Redis 约 10ms，也没有暴露出单条明显异常 SQL。现有证据说明它确实有较高访问下的总体成本，但当前样本不足以说明存在一个明确、稳定的单点瓶颈。

**[建议]**  
先按页面初始化装配成本来处理，重点检查查看页是否存在重复查历史、重复查状态或重复查已读信息。当前证据不足以直接下结论说是某条 SQL 或某个下游依赖导致，建议继续补更慢的样本再压实主因。

## SpringController/${url.rest.prefix.flowmobileapi.v1}/process-drive/task-candidate-infos (POST)

**[现状]**  
这个入口的主问题是数据库驱动的候选信息装配。live 指标显示合并后请求约 4.74 万、错误约 185、平均耗时约 152ms。代表性样本耗时约 143ms，其中数据库查询 36 次、累计约 121ms，占主要部分；控制器自身耗时只有约 17ms。最重的一条 SQL 落在 `LAS_CONTRACT_INFO_CE1`，同时还伴随流程历史相关查询。现有证据说明这里的主要成本不是控制器逻辑，而是候选信息组装时的查库过程。

**[建议]**  
优先检查候选信息查询的 SQL 组合方式，尤其是 `LAS_CONTRACT_INFO_CE1` 和流程历史相关查询是否存在重复触发或可批量化空间。这个入口已经可以明确按数据库装配优化方向处理，不需要先从控制器代码本身找问题。
