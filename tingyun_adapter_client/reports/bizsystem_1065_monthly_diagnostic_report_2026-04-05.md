## 1. 报告摘要

过去 30 天内，`集团法务` 业务系统整体平均指标并不差，但存在明显的“长尾异常”问题：平均响应时间仅 `73ms`，平均吞吐率 `6.44 TPS`，`Apdex=0.914`，系统级错误率 `0.26%`，说明大多数请求仍然较快；但与此同时，少量事务出现了分钟级甚至接近半小时级的极端慢响应，并且至少有一条真实用户上传链路出现了 `120s+` 的失败请求。

从开发调优角度看，这个系统当前最值得关注的不是“整体平均慢”，而是以下两类问题：

- 少量低频但极端慢的事务拉高了尾延迟，且其中一部分事务名称、URI、执行栈之间存在明显不一致，提示存在事务归类异常、初始化逻辑混入请求链路、或请求入口埋点命名不准确的问题。
- 存在明确的用户侧失败链路：`AttachmentController/upload` 在月度窗口内出现两次调用、两次慢请求、两次错误，请求时长达到 `120s~126s`，并在 trace 中明确落到了 `CwSSOFilter.doFilter` 上，优先级应高于“低频超慢但无报错”的后台型调用。

本报告的核心判断是：

1. 当前系统不是“整体不可用”，而是“尾部严重失真”。  
2. `Action health` 只提示了 `1` 个 warning action，但月度热点列表出现了多条分钟级事务，说明当前健康评分不足以覆盖这类低频极端长尾。  
3. 开发侧需要同时处理两件事：
   - 修复真实失败请求
   - 识别并隔离不应混入月度热点榜单的初始化型/统计型事务

### 5.1 现象

`URI/grcv5/user/component/AttachmentController/upload`

这意味着最近一个月里，该事务只要被调用就会：

对开发团队来说，这已经不是“性能优化建议”，而是明确的功能可用性问题。

### 5.2 代表性 trace

选取的典型 trace：

- HTTP 状态：`500`
- 响应时间：`126617.076 ms`
- URI：`/grcv5/user/component/AttachmentController/upload`
- 线程：`http-nio-8888-exec-19`

### 5.3 trace 中的关键可疑点

trace detail 给出的主要问题点有：

1. `org.springframework.web.util.NestedServletException`
2. `com.hd.rcugrc.product.common.authentication.CwSSOFilter.doFilter`
   - `exclusiveTime=126609.447 ms`
   - `metricType=CODE`
3. `metricType=NOSQL`

这组证据的含义非常直接：

- 该请求最终以 `500` 结束
- 主要耗时并没有集中在业务 Controller 本体，而是集中在过滤器链上的 `CwSSOFilter.doFilter`
- NoSQL 被识别为下游组件，但从当前 trace 摘要看，它不是主耗时来源

### 5.4 技术判断

当前最合理的判断是：

- 这条上传失败链路的主要瓶颈更像发生在认证、会话校验、单点登录、令牌校验或过滤器内的同步外部调用上
- 即便有 Redis / NoSQL 参与，也更像“被动参与”而非主导耗时点
- `NestedServletException` 说明请求最终进入了 Spring 包装异常路径，但当前 adapter 摘要没有拿到更深的异常明文，需要继续在应用日志和 call tree 中定位

### 5.5 调优建议

建议按下面顺序排查：

1. 直接检查 `CwSSOFilter.doFilter` 是否存在同步远程调用、阻塞式重试、超时过长或串行鉴权逻辑。  
2. 核查过滤器是否在上传前读取了大对象、会话上下文或外部身份信息，并且没有超时保护。  
3. 对该链路加分阶段耗时日志：
   - 进入过滤器
   - 完成鉴权
   - 进入 Controller
   - 文件落盘/对象存储
   - 返回响应  
4. 对上传接口单独设置更明确的异常日志，把 `NestedServletException` 的根异常打出来。  
5. 如果上传链路依赖 Redis 票据或分布式会话，检查是否存在：
   - Redis 连接抖动
   - 获取锁等待
   - 会话序列化/反序列化异常重试

### 5.6 优先级

`P0`

原因不是它最慢，而是它同时具备：

- 真实用户入口
- HTTP 500
- 100 秒级耗时
- 连续两次调用全部失败

## 6. 重点问题二：`afterPropertiesSet` 被识别为月度第一慢事务

### 6.1 现象

`SpringController/ProductIndexController.afterPropertiesSet`

月度指标：

- 平均响应时间：`1676889 ms`
- 总耗时：`16768888 ms`
- 调用次数：`10`
- 慢请求数：`10`

换算后，平均单次接近 `28` 分钟。

### 6.2 这条事务为什么值得特别谨慎看待

这条事务本身就非常异常，因为：

- Action 名称看起来像 Spring Bean 初始化方法：`afterPropertiesSet`
- 但代表性 trace 的实际请求 URI 却是：
  - `/grcv5/api/flow-mobile/v1/task-form-process/done-pages/399920`
- 请求方法是 `GET`
- call tree 节点数达到 `3003`

也就是说，当前听云命名里的“事务名称”与“真实请求 URI”并不一致。

这通常意味着下面几种可能：

1. 事务命名被框架层方法覆盖了，真正的业务 URI 没有被稳定地命名出来。  
2. 某个初始化逻辑被延迟到首个请求或特定请求中执行，导致用户请求承载了初始化成本。  
3. 埋点归类规则存在偏差，把一个真实业务请求归类到了 `afterPropertiesSet` 这类框架方法上。  

### 6.3 下游组件特征

该事务 overview 中显示：

- Database 调用次数：`2333`
- NoSQL 调用次数：`1449`
- 月度调用次数：`10`

粗略折算后，相当于每次调用平均伴随：

- 约 `233` 次数据库访问
- 约 `145` 次 Redis / NoSQL 访问

这强烈暗示该事务存在明显的“下游访问过密”问题，典型风险包括：

- N+1 查询
- 大量逐条读取与拼装
- 初始化阶段批量预热
- 循环内 Redis / DB 交替访问

### 6.4 代表性 trace

代表性 trace 摘要：

- 响应时间：`16687.523 ms`
- 状态码：`200`
- 实例：`nbyd-jtfw-server2:8888`
- URI：`/grcv5/api/flow-mobile/v1/task-form-process/done-pages/399920`

关键可疑点：

1. `javax.servlet.ServletRequestListener.requestInitialized`
   - `exclusiveTime=7881.945 ms`
   - `metricType=CODE`
2. `metricType=DATABASE`
   - `count=1720`
   - `exclusiveTime=823.994 ms`

### 6.5 技术判断

这条事务最值得关注的不是单次 trace 的 `16.7s`，而是“月度聚合接近 28 分钟 + 名称异常 + 请求初始化热点 + 大量 DB/Redis 调用”这四个信号叠加在一起。

当前判断如下：

- 事务命名/归类大概率存在问题，需要先确认这是否真的是一个用户请求，而不是把某个初始化逻辑算进了 Controller 事务。
- 即便命名存在问题，下游访问次数也异常高，说明这条链路确实存在重型数据装载或循环调用行为。
- `requestInitialized` 成为最大独占时间点，提示性能问题可能出现在请求初始化阶段、监听器、过滤器前置逻辑或某类上下文构造逻辑，而不是单纯的 Controller 内部 SQL。

### 6.6 调优建议

建议分两条线同时排查：

1. 命名与归类线  
   - 核查听云事务命名规则是否被 `afterPropertiesSet` 覆盖  
   - 核查是否存在首请求触发延迟初始化  
   - 对移动端 `done-pages/{id}` 链路单独建立事务命名或别名，避免和框架方法混淆  

2. 性能与访问密度线  
   - 审查该链路中的 DB / Redis 调用次数，优先找循环内调用  
   - 对对象装载、权限拼装、待办聚合逻辑做分段统计  
   - 排查是否存在一次请求里预热大量缓存、批量拼装页面模型的行为  
   - 优先处理“每次请求需要触发数百次 DB/Redis 访问”的代码模式  

### 6.7 优先级

`P1`

原因是：

- 它的绝对耗时最严重
- 但从当前证据看，它未必是最直接的用户失败面
- 需要先做一次“分类澄清”，再决定是否作为核心业务链路优化

## 7. 重点问题三：`lawyerEorkTimeTop10Data.dwr` 为典型重报表/重聚合事务

月度热点中，同一业务逻辑在两个应用上下文下都进入了 Top 3：

- `actionId=31762`，平均 `1541760 ms`，调用 `2` 次
- `actionId=31342`，平均 `1519501 ms`，调用 `3` 次

这类事务的特征非常像：

- 报表型接口
- 排行榜/TopN 统计
- 跨时间范围聚合
- 多维度数据拼装

从命名上看，`lawyerEorkTimeTop10Data` 本身就很像一个“工作量排行/统计型接口”。

### 技术判断

这类事务即使不是高频用户主链路，也很值得专项治理，因为：

- 它们耗时极端高
- 出现在两个不同应用上下文，说明代码模式可能被复制或复用
- 往往意味着 SQL 聚合代价高、索引不匹配、扫描范围过大，或者统计逻辑没有离线化/缓存化

### 调优建议

1. 把该接口拆成“在线查询”与“离线统计”两层。  
2. 核查底层 SQL 是否走了大范围排序、临时表、全表扫描。  
3. 对 Top10 这类固定结果集场景优先使用缓存或预计算。  
4. 检查两个应用上下文是否共享了同一份重逻辑，避免重复优化。  

### 优先级

`P1`

`SpringController/TemplateUploadController.setTemplateService`

月度指标：

- 平均响应时间：`335812 ms`
- 调用次数：`11`
- 慢请求数：`6`
- 错误数：`0`

这说明该链路虽然没有报错，但存在明显的高耗时处理。

### 技术判断

该链路很可能涉及：

- 模板加载/解析
- 大文件处理
- 同步远程对象存储/文件系统操作
- 模板元数据刷新

2. 将可异步的模板预处理、转换、索引构建移到后台。  
3. 对文件处理过程增加阶段耗时日志，确认究竟慢在：
   - I/O
   - 模板解析
   - 数据库保存
   - 缓存刷新

- 对失败链路保留根异常而非仅保留包装异常

## 12. 结论

`集团法务` 在最近一个月内，整体均值表现尚可，但已经出现了明显的“低频极端长耗时 + 局部失败链路”特征。对开发团队而言，当前最重要的不是再看平均值，而是优先治理下面两类问题：

- 明确失败、直接影响用户的上传链路
- 极端慢、命名异常、下游访问密集的初始化/统计型事务

如果这两类问题不处理，系统即使平均响应仍然漂亮，也会持续出现：

- 页面偶发极慢
- 上传失败
- 热点榜单被异常事务污染
- 难以从均值指标中直观看出真实风险

从调优收益与业务风险综合判断，建议开发团队将本次月度治理主线定义为：

**“先修失败，再拆长链路，再治理重聚合与初始化混入。”**
